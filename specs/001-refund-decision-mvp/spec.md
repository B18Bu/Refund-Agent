# Feature Specification: 多 Agent 协同客诉舆情退赔决策系统（MVP）

**Feature Branch**: `001-refund-decision-mvp`

**Created**: 2026-08-18

**Status**: Draft

**Input**: User description: "实现多 Agent 协同客诉舆情退赔决策系统 MVP：客服提交工单后自动执行 OCR→风控→舆情→金额决策链路，高风险转主管人工审批"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 客服登录并提交退赔工单 (Priority: P1)

客服登录系统后，填写客诉金额、客诉描述并上传凭证图片，提交后系统受理并返回工单编号，
客服可随时查看本人提交的工单列表与详情。

**Why this priority**: 这是整个系统的入口，没有工单就没有后续任何自动化决策；是必须最先交付、可独立验证的最小闭环。

**Independent Test**: 单独交付登录与建单能力即可验证 —— 客服登录 → 提交工单（含图片）→ 收到工单编号 → 列表与详情可见。

**Acceptance Scenarios**:

1. **Given** 客服已登录，**When** 提交金额、描述与合法凭证图片，**Then** 系统受理并返回唯一工单编号，工单进入待处理状态。
2. **Given** 客服已登录，**When** 提交金额为空或非正数，**Then** 系统拒绝受理并给出明确错误提示。
3. **Given** 客服已登录，**When** 上传非图片或超大文件，**Then** 系统拒绝该文件并提示格式/大小限制。
4. **Given** 客服已登录，**When** 查看工单列表，**Then** 只能看到本人提交的工单。

---

### User Story 2 - 低风险工单自动退赔决策 (Priority: P1)

工单提交后，系统自动完成凭证识别、风险分析与金额判定；对金额小、凭证清晰可信、无欺诈/舆情
风险的工单，无需人工干预直接给出自动退赔结论。

**Why this priority**: 自动退赔是系统"提效、统一标准"的核心价值；低风险自动放行路径必须优先打通，才能证明多 Agent 决策链路可用。

**Independent Test**: 提交一笔小金额 + 清晰凭证 + 低风险工单，系统在无人工干预下自动产生"自动退赔"结论并展示决策依据。

**Acceptance Scenarios**:

1. **Given** 工单金额 ≤ 300 元、凭证识别可信、风险分低、舆情等级为低，**When** 自动决策链路执行完成，**Then** 工单直接得到"自动退赔"结果。
2. **Given** 凭证图片无法识别或可信度不足，**When** 自动决策链路执行，**Then** 系统不自动退赔，转人工审批。
3. **Given** 风险或舆情分析判断存在异常，**When** 决策链路执行，**Then** 系统不自动退赔，转人工审批。

---

### User Story 3 - 高风险/不确定工单转主管人工审批 (Priority: P1)

对金额超限、凭证不可信、欺诈/舆情风险高的工单，系统暂停自动流程、保留中间状态，转由主管
审批；主管作出批准或拒绝后，系统从暂停处恢复并得出最终结果。

**Why this priority**: 人工兜底是资损安全的最后防线；"宁挂勿错退"是系统的核心红线，必须在 MVP 内闭环。

**Independent Test**: 提交一笔金额 > 300 元的工单 → 系统进入"待人工审批"状态 → 主管审批（批准/拒绝）→ 工单得到最终结果。

**Acceptance Scenarios**:

1. **Given** 工单触发人工审批条件（金额超限/凭证不可信/风险高），**When** 决策链路执行到审批点，**Then** 工单进入"待人工审批"状态且中间结果被保留。
2. **Given** 主管对挂起工单作出批准，**When** 审批提交，**Then** 工单从断点恢复并得到"已批准"最终结果。
3. **Given** 主管对挂起工单作出拒绝，**When** 审批提交，**Then** 工单得到"已拒绝"最终结果。
4. **Given** 非主管角色（客服）尝试审批，**When** 调用审批，**Then** 系统拒绝该操作（无审批权限）。
5. **Given** 系统服务在工单挂起期间重启，**When** 服务恢复，**Then** 挂起工单及其中间状态不丢失，主管仍可审批并从断点恢复。

---

### User Story 4 - 大屏实时展示决策过程 (Priority: P2)

主管在大屏可实时查看工单列表、各决策环节的执行路径、凭证识别文本、风险评分与审批入口，
工单状态变化即时可见。

**Why this priority**: 可视化让多 Agent 决策过程"可看见、可信任"，是演示与验收的关键能力，但不阻塞核心决策链路。

**Independent Test**: 提交一笔工单后，大屏实时出现该工单，并随决策推进逐步展示各环节状态与结果，最终展示审批入口或最终结论。

**Acceptance Scenarios**:

1. **Given** 有工单在执行或已完成，**When** 打开大屏，**Then** 能看到工单列表及各环节执行状态。
2. **Given** 某工单决策推进到新环节，**When** 状态变化，**Then** 大屏在无需手动刷新下及时更新（断线后自动恢复刷新）。
3. **Given** 工单处于"待人工审批"，**When** 当前用户为主管，**Then** 大屏展示审批面板供其操作。

---

### User Story 5 - 防重复提交与并发审批互斥 (Priority: P2)

同一客服对同一提交的重复请求只产生一张工单；同一工单被多名主管同时审批时，仅第一笔有效，
其余被拒绝，杜绝重复退赔或重复审批。

**Why this priority**: 退款重复执行即资损、并发审批即状态错乱；这是资金安全类红线，必须覆盖，但可作为对核心流程的加固独立验证。

**Independent Test**: 以相同提交标识重复/并发提交工单 → 仅生成一张工单；两名主管并发审批同一挂起工单 → 仅一条审批生效，另一条被拒绝。

**Acceptance Scenarios**:

1. **Given** 客服以相同提交标识重复或并发提交，**When** 系统处理，**Then** 只创建一张工单，重复请求返回首次工单。
2. **Given** 两名主管并发审批同一挂起工单，**When** 系统处理，**Then** 仅第一笔审批生效，另一笔收到冲突提示。
3. **Given** 已完成工单被再次审批，**When** 系统处理，**Then** 系统拒绝并提示状态冲突。

---

### User Story 6 - 决策全程可审计 (Priority: P3)

任一工单的决策过程（各环节输入/输出、风险结果、审批人、审批意见、失败原因）均可追溯查询，
用于问题排查与合规。

**Why this priority**: 审计可回放是"可追责、可排查"的底座，价值重要但可后置完善，不阻塞 MVP 主流程。

**Independent Test**: 任取一张已处理工单，可查询到其完整的决策环节记录、审批人与审批意见、失败时的错误原因。

**Acceptance Scenarios**:

1. **Given** 工单已完成或失败，**When** 查看详情，**Then** 能追溯各决策环节的记录与关键结果。
2. **Given** 工单失败，**When** 查看详情，**Then** 能看到明确的失败原因（错误码/说明），且不暴露敏感凭据。

---

### Edge Cases

- 同一客服以相同提交标识重复/并发建单时，如何保证只产生一张工单？
- 两名主管同时审批同一挂起工单时，如何保证只产生一条有效审批？
- 凭证图片损坏、无法识别、或识别置信度过低时，系统如何兜底（不自动放行）？
- 云端风险/舆情分析超时、返回非法格式或取值越界时，系统如何兜底（保守转人工）？
- 工单在挂起期间系统重启，中间状态与审批能力是否保留？
- 审批已成功但后续处理投递失败时，如何保证可恢复或可人工补偿？
- 客服越权查看他人工单、或非主管越权审批时，系统如何拒绝？

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 支持客服与主管两类用户登录并区分身份。
- **FR-002**: 系统 MUST 允许客服/主管提交工单（金额、客诉描述与凭证图片），并为每张工单生成唯一编号。
- **FR-003**: 系统 MUST 校验凭证图片的格式（仅 JPG/JPEG/PNG）与大小（单文件 ≤ 10MB，每单最多 3 张）。
- **FR-004**: 系统 MUST 在工单提交后自动执行"凭证识别 → 风险分析 → 舆情分析 → 金额决策"链路。
- **FR-005**: 系统 MUST 根据确定性规则路由：金额 > 300 元、凭证识别可信度 < 0.60、欺诈风险分 ≥ 50、或舆情等级非"低"，任一满足即转人工审批；否则自动退赔。
- **FR-006**: 系统 MUST 在转人工审批时暂停流程并完整保留中间状态，审批后从断点恢复。
- **FR-007**: 系统 MUST 仅允许主管执行审批（批准/拒绝），客服无审批权限。
- **FR-008**: 系统 MUST 对重复/并发提交进行幂等控制，同一提交标识只创建一张工单。
- **FR-009**: 系统 MUST 对同一工单的并发审批进行互斥，仅一笔审批生效，其余返回冲突。
- **FR-010**: 系统 MUST 保留每张工单的决策轨迹（各环节输入/输出、风险结果、审批人、审批意见、失败原因）。
- **FR-011**: 系统 MUST 提供大屏视图，展示工单列表、各环节执行状态、凭证识别文本、风险评分与审批入口。
- **FR-012**: 系统 MUST 在工单状态变化时实时通知大屏，并在断线后自动恢复刷新。
- **FR-013**: 系统 MUST 对任何模型不确定或分析失败的情况采取保守策略，绝不自动放行。
- **FR-014**: 系统 MUST 保证挂起工单在系统重启后不丢失，且可继续审批。

### Key Entities *(include if feature involves data)*

- **用户（User）**: 系统的操作者，区分为客服与主管两种角色；主管拥有审批权限。
- **工单（Ticket）**: 一次客诉退赔申请，包含金额、客诉描述、当前状态与最终结果；是决策流程的载体。
- **凭证文件（Evidence File）**: 工单关联的图片证据，含格式、大小、唯一标识与完整性校验信息。
- **审批记录（Approval）**: 主管对挂起工单作出的批准/拒绝决定，含审批人、动作与意见；每张工单至多一条有效审批。
- **决策轨迹（Trace）**: 工单各决策环节的执行记录（环节名、状态、输入/输出摘要、失败原因），用于展示与审计。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 客服从登录到提交工单并获得受理回执可在 1 分钟内完成。
- **SC-002**: 符合条件的低风险工单可在无人工干预下自动得到"自动退赔"结论。
- **SC-003**: 100% 的高风险或不确定工单进入人工审批，不发生任何错误自动放行（资损零容忍）。
- **SC-004**: 主管对挂起工单审批后，工单能恢复并得到最终结果，且服务重启不丢失挂起状态。
- **SC-005**: 重复/并发提交不产生重复工单；并发审批仅一笔生效（数据唯一性可验证）。
- **SC-006**: 系统在至少 200 名客服同时操作时不出现明显延迟或请求失败。
- **SC-007**: 任一张工单的决策过程可完整追溯（谁在何时做了什么、失败原因明确）。

## Assumptions

- 目标用户为内部客服与主管，均有稳定的网络环境，使用桌面浏览器访问。
- 凭证仅限图片（JPG/JPEG/PNG），MVP 不支持 PDF/视频/音频等复杂凭证。
- "舆情风险"指基于工单材料的风险等级判断，不涉及对外部互联网舆情数据的抓取。
- "自动退赔"仅指系统生成并记录退赔决策结论，MVP 不执行真实支付/资金划转。
- 风险与舆情分析默认由 DeepSeek（OpenAI 兼容接口，api_key 认证）提供，接口保持可替换。
- 演示环境需预置至少 1 名客服与 1 名主管账号；生产账号经初始化脚本或管理员创建。
- 移动端适配不在 MVP 范围内。
