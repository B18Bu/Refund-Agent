## 2. 核心议题逐项讨论

### 议题 1：状态挂起与恢复机制（★ 核心）

**要解决的问题**：决策流运行到人工审批节点时如何暂停、如何保存中间状态、如何从断点恢复。

| 参与方 | 方案 | 依据/风险 |
| --- | --- | --- |
| AI-A | `redis.set(f"checkpoint:{id}", pickle.dumps(graph_state))` 手动序列化图状态，恢复时反序列化重新注入 | 简单直接；但手写 pickle 有版本兼容、安全、序列化一致性风险 |
| AI-B | LangGraph 原生 `interrupt()` + Redis Checkpointer；不手工 pickle；恢复用 `Command(resume=...)` + 同一 `thread_id`；API 不直接 resume，写 RESUME 消息由 Worker 串行恢复 | 原生中断语义；避免 API 与 Worker 争抢图状态；checkpoint 缺失兜底 `FAILED + CHECKPOINT_NOT_FOUND` |
| 人工方 | `human_review_node` 用 `interrupt({"ticket_id","message"})`；`RedisSaver.from_conn_string` 作 checkpointer；初跑用 `graph.stream()` 避免 interrupt 抛异常，`graph.get_state(cfg).next` 判定是否挂在 human_review；恢复用 `Command(resume={"action": APPROVE})` | 与 AI-B 一致，且补充了「stream 避 interrupt 异常」的版本兼容技巧 |

**分歧点**：是否手工 pickle（AI-A）vs 原生 interrupt + Checkpointer（AI-B / 人工方）。

**对齐结论**：✅ 采用 **LangGraph 原生 `interrupt()` + Redis Checkpointer + `Command(resume=...)`**，否决手工 pickle。三态 `RUNNING / SUSPENDED / COMPLETED` 三方一致。人工方补充的「`graph.stream()` 初跑 + `get_state().next` 判定挂起」作为实现细节写入基线。

---

### 议题 2：超时任务解耦（★ 核心）

**要解决的问题**：OCR / LLM 为长耗时任务，不能阻塞 API 请求；需保证任务不因服务重启丢失、可横向扩容。

| 参与方 | 方案 | 依据/风险 |
| --- | --- | --- |
| AI-A | FastAPI `BackgroundTasks` 启动异步任务，后续迁移 Celery | MVP 够用；但任务与 API 同进程，服务重启即丢失，无法独立扩容 |
| AI-B | Redis Streams + 独立 Worker（消费组 XADD/XREADGROUP/XACK）；API 只投递，Worker 长任务；成功后才 XACK，异常保留 Pending 供重试 | 进程解耦、可恢复、可扩容 |
| 人工方 | 同 AI-B：`stream:tickets` + `worker-group`，API `xadd`，Worker `xreadgroup` + `xack`，`while True: run_once()` 循环 | 与 AI-B 一致 |

**分歧点**：BackgroundTasks（AI-A）vs Redis Streams + Worker（AI-B / 人工方）。

**对齐结论**：✅ 采用 **Redis Streams + 独立 Worker 消费组**，否决 BackgroundTasks（进程内执行、重启丢失、不可扩容）。补充对齐：Worker 异常时**不 XACK**、保留 Pending Entry，不可恢复错误落库 `FAILED + error_code` 后再确认。

---

### 议题 3：高并发防重与分布式锁（★ 核心）

**要解决的问题**：同一请求重复/并发提交不产生重复工单；同一挂起工单不被多名主管并发审批。

| 参与方 | 幂等方案 | 锁方案 | 依据/风险 |
| --- | --- | --- | --- |
| AI-A | `X-Idempotency-Key` + Redis `SETNX`，TTL 24h | 审批用分布式锁，未细化释放机制 | 幂等可行；锁释放未落地 |
| AI-B | `SET NX EX 86400` + PostgreSQL 联合唯一索引兜底 | `SET lock:{id} {random_token} NX PX 10000`；释放用 **Lua 脚本比较 token 后删除**，禁止无条件 DEL；DB 条件更新 `WHERE status='SUSPENDED'` | 锁释放安全性是红线（防止误删他人新锁） |
| 人工方 | `resolve_idempotency`：`redis.set(nx=True, ex=86400)`，重复返回原工单 | `acquire_approve_lock`：`set(nx=True, px=10000)`；但 `release_approve_lock` 用 **`redis.delete()` 无条件 DEL**，锁值固定 `"1"` | ⚠️ 释放存在竞态缺陷：锁过期后可能误删他人的新锁 |

**分歧点**：① 锁释放是否用 token + Lua（AI-B 要求，人工方实现为无条件 DEL）；② 锁值是否随机。

**对齐结论**：✅ 幂等三方一致（`SET NX` + DB 唯一索引兜底）。⚠️ 锁释放**必须对齐到 AI-B**：锁值改随机 token，释放改为「比较 token 后 Lua 脚本删除」，**禁止无条件 DEL**——人工方 `release_approve_lock` 记为**必须修复项**。

| 参与方 | 表结构 | 迁移方式 |

### 议题 7：失败语义与错误码

| 参与方 | 方案 |
| --- | --- |
| AI-A | status 含 rejected，无明确 FAILED 语义 |
| AI-B | `COMPLETED + FAILED + error_code` 表达失败，保留三态；checkpoint 缺失 → `CHECKPOINT_NOT_FOUND` |
| 人工方 | `Decision` 枚举仅 PENDING / AUTO_REFUNDED / APPROVED / REJECTED，**无 FAILED**；Worker 异常仅 `print`，不落库 |

**分歧点**：是否需要 FAILED 状态与 error_code。

**对齐结论**：⚠️ **补充 FAILED 与 error_code**（采纳 AI-B）。人工方需在 `Decision` 枚举增加 `FAILED`，Worker 异常时写 `FAILED + error_code` 后再 XACK。记入待办。

### 议题 8：决策规则纯函数签名

## 4. 对齐后的最终技术基线

经三方对齐，最终基线以 **AI-B 规范为骨、人工方代码为肉**，收敛如下：

| 维度 | 最终基线 |
| --- | --- |
| 架构 | FastAPI（生产者）+ Redis Streams + Worker（消费者）+ LangGraph Checkpointer |
| 状态机 | `RUNNING → SUSPENDED → COMPLETED` 三态 + `PENDING/AUTO_REFUNDED/APPROVED/REJECTED/FAILED` 五结果 |
| 挂起恢复 | `interrupt()` + Redis Checkpointer + `Command(resume=...)` + 同一 `thread_id`；不手工 pickle |
| 超时解耦 | API 只投递消息，Worker 长任务；成功 XACK、异常保留 Pending、不可恢复落 FAILED 后确认 |
| 防重 | `X-Idempotency-Key` + `SET NX EX 86400` + DB 联合唯一索引兜底 |
| 锁 | `SET lock:{id} {random_token} NX PX 10000` + **Lua 比较 token 删除** + DB 条件更新 |
| OCR | 本地 PaddleOCR，输出文字 + 置信度，可替换接口 |
| LLM | DeepSeek（OpenAI 兼容），可替换适配器 |
| 决策规则 | 无 I/O 纯函数 `decide(amount, ocr_confidence, fraud_score, sentiment)`，单测覆盖 |
| 数据模型 | users / tickets（含 error_code）/ approvals / agent_traces（凭证用 JSON 字段，MVP 简化） |
| 认证 | JWT 仅 Access Token，2 小时；主管独占审批，服务层数据范围过滤 |
| 实时推送 | SSE + 断线 2 秒轮询降级 |
| 部署压测 | Docker Compose；Locust 验收 QPS≥200、P95<300ms、错误率<0.1% |

## 结论

三方在**总体架构与六大原始需求**上达成一致，分歧集中在实现严谨度。本次对齐的实质结论是：

1. **状态挂起**：弃用 AI-A 的手工 pickle，统一为 LangGraph 原生 interrupt + Redis Checkpointer。
2. **超时解耦**：弃用 AI-A 的 BackgroundTasks，统一为 Redis Streams + 独立 Worker。
3. **高并发防重**：幂等方案三方一致；分布式锁必须补齐 token + Lua 释放（修复人工方无条件 DEL 缺陷）。

人工方的实现计划作为**主要编码基线**沿用，但需按 A-01 ~ A-07 完成 3 项 P0 修复与 4 项 P1 增强后，方可作为最终验收口径。
