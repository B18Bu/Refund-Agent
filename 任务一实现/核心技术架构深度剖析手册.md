# 第一部分 · 架构力板块

## ① LangGraph 无状态服务设计（结合 Redis Checkpointer）

### 1.1 问题本质：图的「定义」与「执行」要分离

一个 LangGraph 工作流天然包含两类截然不同的东西：

| 维度 | 内容 | 是否可变 | 存放位置 |
| --- | --- | --- | --- |
| **图定义** | 节点函数（intake/evidence/fraud/sentiment/decision）、边、条件路由 | 编译后不变 | 代码内，进程内存，可重复构建 |
| **执行状态** | `GraphState` 快照 + 节点执行历史 + 中断点 | 每次执行都在变 | 必须外置持久化 |

无状态服务设计的关键动作，就是**把第二类（执行状态）从进程内存中剥离出去**，交给 Redis Checkpointer 统一管理。这样，承载图执行的 Worker 进程本身就不再持有任何业务状态，成为「随起随用、随停随走」的无状态服务。

### 1.2 LangGraph 执行模型

```text
StateGraph(GraphState)
   └─ compile(checkpointer=RedisSaver)      ← 注入 Checkpointer，状态外置
          │
          ├─ invoke(state, config={"thread_id": t})
          │        └─ 每个 super-step 后，Checkpointer 把 (状态快照 + 历史) 写入 Redis
          │
          ├─ interrupt({...})               ← 人工节点主动中断，checkpoint 落盘
          │
          └─ invoke(Command(resume=...), config={"thread_id": t})
                   └─ 从 Redis 读回 checkpoint，从断点继续
```

核心概念：

- **`thread_id`**：一次完整执行（含挂起→恢复）的逻辑会话 ID，是定位 checkpoint 的唯一键。同一工单的初始执行与恢复执行必须复用同一 `thread_id`。
- **`interrupt()`**：在 `human_review` 节点主动挂起，LangGraph 会把当前状态 + 待恢复位置写入 checkpoint，图进入暂停态。
- **`Command(resume=...)`**：注入外部输入（如主管的 `APPROVE`/`REJECT`），从 interrupt 处继续往下跑。
- **Checkpointer**：LangGraph 的状态持久化抽象。`RedisSaver`（`langgraph-checkpoint-redis`）把状态序列化到 Redis，是「无状态 Worker + 有状态执行」的粘合层。

### 1.3 为什么 Redis Checkpointer 使服务「无状态」

| 无状态化收益 | 具体体现 |
| --- | --- |
| **崩溃可恢复** | Worker 被杀后，重启即可从 Redis 读回 checkpoint 继续，不丢执行进度 |
| **水平可扩容** | 任意 Worker 实例都能消费任意消息、推进任意 `thread_id` 的图——状态从 Redis 读写，不依赖本地内存 |
| **进程解耦** | API 与 Worker 是两类进程，都通过 Redis 读写状态，互不争抢 |
| **可观测/可回放** | checkpoint 保留执行历史，故障排查时可还原节点级轨迹 |

### 1.4 三条设计红线（无状态化的前提）

1. **同一 thread 用同一 Checkpointer**：初始执行与恢复必须连同一 Redis、同一 `thread_id`，否则恢复会找不到状态。
2. **不手工 pickle**：挂起走原生 `interrupt()` + Checkpointer，禁止自行 `pickle.dumps(graph_state)`——手工序列化会破坏 LangGraph 的状态版本兼容与校验。
3. **API 不直接 `resume()`**：恢复必须由 Worker 串行执行。若 API 直接 resume，会与 Worker 同时操作同一 checkpoint，产生「两边基于旧状态推进」的竞态。

```python
# 正确姿势：API 只投递 RESUME 消息，Worker 统一串行恢复
def process(fields: dict):
    with RedisSaver.from_conn_string(settings.REDIS_URL) as checkpointer:
        graph = build_graph().compile(checkpointer=checkpointer)
        cfg = {"configurable": {"thread_id": fields["thread_id"]}}
        if fields.get("resume_action"):
            graph.invoke(Command(resume={"action": fields["resume_action"]}), config=cfg)  # 恢复
        else:
            for _ in graph.stream(initial, config=cfg):          # 初次执行
                pass
```

## ② 生产者-消费者异步长任务处理流向（FastAPI + Redis Streams + Worker）

### 2.1 为什么用生产者-消费者解耦

OCR（PaddleOCR）与 LLM（DeepSeek）是**长耗时、重资源**的任务。若在 API 请求内同步执行，会阻塞请求、耗尽连接、拖垮 P95。因此将「受理」与「执行」拆成两个独立进程，通过 Redis Streams 传递任务。

### 2.2 整体流向图

```text
┌──────────── 生产者：FastAPI API ────────────┐
│ POST /api/tickets                           │
│   1. 鉴权 / 校验 / 幂等                     │
│   2. 落库 tickets (status=RUNNING)          │
│   3. XADD stream:tickets  START 消息        │
│   4. 返回 202 Accepted                      │
│                                             │
│ POST /api/tickets/{id}/approval             │
│   1. SETNX 审批锁 / 校验状态                │
│   2. 落库 approvals                         │
│   3. XADD stream:tickets  RESUME 消息       │
│   4. 释放锁 / 返回                          │
└──────────────────┬──────────────────────────┘
                   │  XADD（写入 Stream）
                   ▼
┌──────────── Redis Streams ──────────────────┐
│ stream:tickets + worker-group（消费组）      │
│  ├─ 已交付待确认：Pending Entries List(PEL) │
│  └─ 未交付：> 游标                           │
└──────────────────┬──────────────────────────┘
                   │  XREADGROUP（阻塞拉取）
                   ▼
┌──────────── 消费者：Worker（可横向扩容）────┐
│ while True:                                 │
│   msgs = XREADGROUP(group, consumer, {key:">"}, block=5000) │
│   for msg in msgs:                          │
│       process(fields)                       │  ← 执行/恢复 LangGraph 图
│       XACK stream key msg_id   (成功)        │
│       # 失败则不入 XACK，保留 Pending 供重试 │
└─────────────────────────────────────────────┘
```

### 2.3 消息契约

```json
// START：初始执行
{ "type": "START", "ticket_id": "1", "thread_id": "lg_1", "created_at": "..." }

// RESUME：主管审批后恢复
{ "type": "RESUME", "ticket_id": "1", "thread_id": "lg_1", "resume_action": "APPROVE", "approval_id": "9" }
```

### 2.4 消息生命周期与可靠性语义

| 阶段 | 动作 | 语义 |
| --- | --- | --- |
| 生产 | `XADD` | 追加到 Stream 尾部，返回消息 ID |
| 消费 | `XREADGROUP ... ">"` | 只读「本组未交付」的新消息 |
| 确认 | `XACK` | **成功处理后**才确认，从 PEL 移除 |
| 失败 | 不 `XACK` | 消息留在 Pending Entries List，可被回收重试 |
| 不可恢复失败 | 落库 `FAILED + error_code` 后 `XACK` | 明确终结，避免死循环 |

关键设计：**先处理、后确认**。只有完整处理成功才 `XACK`；异常不确认，消息保留在 Pending 中供「回收（XCLAIM/XAUTOCLAIM）」重投，保证「至少一次」投递语义。消费端因此必须幂等（按工单状态 + `thread_id` 去重，见议题 ⑧）。

### 2.5 时序示意（金额超限挂起 → 主管审批）

```text
客服     API            Redis Streams      Worker              PostgreSQL
 │ POST /tickets           │                  │                    │
 │─────────▶│ XADD START ──▶│                  │                    │
 │◀──202────│               │                  │                    │
 │          │               │◀──XREADGROUP────│                    │
 │          │               │                  │── 跑图 → interrupt │
 │          │               │                  │── update SUSPENDED─▶│
 │          │ 主管 POST approval                │                    │
 │          │── XADD RESUME─▶│                  │                    │
 │          │               │◀──XREADGROUP────│                    │
 │          │               │                  │── Command(resume)  │
 │          │               │                  │── update COMPLETED─▶│
 │          │               │◀──XACK──────────│                    │
```

# 第二部分 · AI 工程化板块

## ③ 四大 Agent 职责划分（Intake / Evidence / Fraud / Sentiment）

### 3.1 职责边界总览

决策链 = **4 个 AI Agent（采集与归一化）** + **1 个纯函数决策层（路由）** + **1 个中断节点（人工）**。

```text
START
  → Intake（受理）        → 规整基础字段
  → Evidence（凭证采集）  → OCR 提取证据
  → Fraud（欺诈风控）     → 欺诈打分
  → Sentiment（舆情）     → 舆情分级
  → Decision（纯函数）    → 确定性路由，非 Agent
       ├─ AUTO_REFUND → END
       └─ HUMAN_REVIEW（interrupt 中断，非 Agent）→ 主管审批 → END
```

### 3.2 四大 Agent 契约

| Agent | 职责 | 输入 | 输出 | 失败兜底 |
| --- | --- | --- | --- | --- |
| **Intake** | 受理与字段归一化，产出合法 GraphState 初值 | 金额、图片清单、申请人、工单描述 | 规范化 `amount`、`image_paths`、默认分数 | 字段缺失 → 工单 `FAILED` |
| **Evidence** | 凭证证据采集（核心子能力 = OCR），从图片提取文本与置信度 | 受控本地图片路径列表 | `ocr_text`、`ocr_confidence` | 图片损坏/无法识别 → 置信度 `0`，转人工 |
| **Fraud** | 欺诈风控，量化「恶意退款/薅羊毛」风险 | 金额、OCR 文本、工单描述 | `fraud_score: 0..100` | 超时/解析失败 → 保守高分，转人工 |
| **Sentiment** | 舆情风险分级 | 工单描述、OCR 文本 | `LOW / MEDIUM / HIGH` | 超时/非法输出 → 保守 `HIGH`，转人工 |

### 3.3 与决策层的边界（关键工程约束）

- **Agent 只负责「采集 + 归一化」**，不做业务判断；`nodes.py` 只做「调 OCR/LLM + 组装 state」。
- **路由判断全部下沉到 `decision_rules.decide`**（无 I/O 纯函数），是决策正确性的唯一来源，单测覆盖。

```python
# 纯函数：唯一决策来源，可单测
def decide(amount, ocr_confidence, fraud_score, sentiment) -> str:
    if amount > 300 or ocr_confidence < 0.60 or fraud_score >= 50 or sentiment != "LOW":
        return "HUMAN_REVIEW"
    return "AUTO_REFUND"
```

## ④ 大模型 Output Parse 失败的 Fallback 机制

### 4.1 失败类型全景

LLM 输出不可靠，需对每一类失败做结构化兜底：

| 失败类型 | 表现 | 触发示例 |
| --- | --- | --- |
| 网络超时 | 请求超时 | DeepSeek 无响应 |
| 服务端错误 | 5xx / 限流 429 | 模型过载、配额耗尽 |
| 非法 JSON | 输出不是合法 JSON | 模型夹带解释文本 |
| 非法枚举 | JSON 合法但字段/取值越界 | `fraud_score` 返回 `"high"` 或 `120` |
| 字段缺失 | JSON 缺关键字段 | 缺 `fraud_score` 键 |

### 4.2 Fallback 阶梯：重试 → 保守值 → 转人工

```text
                    ┌──────────────────────────────────────────┐
 LLM 调用            │ 1. 结构化输出（temperature=0 + 严格 prompt）│
   │                │ 2. Pydantic 校验输出                       │
   ▼                └───────────────┬──────────────────────────┘
 成功且合法 ────────────────────────┤
                                   │ 失败
                          ┌────────▼────────┐
                          │ 有限重试（≤1 次） │  ← 指数退避
                          │ 结构化解析重试    │
                          └────────┬────────┘
                                   │ 仍失败
                          ┌────────▼─────────────────┐
                          │ 保守值兜底：              │
                          │  Fraud → fraud_score=100 │
                          │  Sentiment → "HIGH"       │
                          └────────┬─────────────────┘
                                   │
                          ┌────────▼─────────────────┐
                          │ 决策层强制 HUMAN_REVIEW    │  ← 宁挂勿错退
                          │ 转主管人工审批             │
                          └──────────────────────────┘
```

### 4.3 代码示意

```python
def fraud_node(state: GraphState) -> GraphState:
    prompt = ("你是退款风控专家。根据凭证 OCR 文本与金额评估欺诈分（0-100 整数）。"
              "只输出 JSON：{\"fraud_score\": <int>}")
    raw = call_llm("你是风控专家。", prompt)
    try:
        state["fraud_score"] = int(json.loads(raw)["fraud_score"])
    except Exception:
        state["fraud_score"] = 100      # 保守兜底：宁挂勿错退
    return state

def sentiment_node(state: GraphState) -> GraphState:
    raw = call_llm("你是舆情专家。", prompt).strip().upper()
    state["sentiment"] = raw if raw in ("LOW", "MEDIUM", "HIGH") else "HIGH"
    return state
```

### 4.4 设计红线

**「宁挂勿错退」**：任何模型不确定性（超时、解析失败、非法输出）都**不允许**落到「自动通过」，而必须收敛到「转人工审批」。这样保证：系统在 AI 不可靠时，只会增加人工负担，绝不会错误放行导致资损。

# 第三部分 · 算法与数据处理板块

## ⑤ PaddleOCR 置信度阈值路由设计

### 5.1 置信度的语义

PaddleOCR 对每个识别框返回一个置信度 `score ∈ [0,1]`。置信度衡量**文本识别的可信度**——低置信度意味着 OCR 可能识别错误，进而污染下游 Fraud/Sentiment 的输入，导致误判。

### 5.2 多图置信度聚合

- 单图：取该图所有文本框置信度的**平均**作为该图置信度。
- 多图（每单 ≤3 张）：取各图置信度的**最小值**作为工单整体置信度——采用「木桶原则」，只要有任一张凭证不可信，即视为整体证据链不可信。

```python
def extract_text(image_path: str) -> tuple[str, float]:
    results = get_ocr().ocr(image_path, cls=True)
    scores = [box[1][1] for line in (results or []) for box in (line or [])]
    return "\n".join(texts), (sum(scores) / len(scores) if scores else 0.0)

# 多图：取最小置信度
state["ocr_confidence"] = min(all_img_confidences) if all_img_confidences else 0.0
```

### 5.3 阈值路由表

| 条件 | 路由结果 | 理由 |
| --- | --- | --- |
| `ocr_confidence ≥ 0.60` | 进入自动决策，可 `AUTO_REFUND` | 证据可信 |
| `ocr_confidence < 0.60` | **强制 `HUMAN_REVIEW`** | 证据不可信，禁止自动放行 |
| 识别失败 / 空结果 | 置信度 `0`，强制人工 | 无证据可用 |

阈值 `OCR_CONFIDENCE_THRESHOLD = 0.6` 作为可配置项（`settings`），便于按业务风险偏好调整。

```python
def decision_node(state: GraphState) -> GraphState:
    d = decide(state["amount"], state["ocr_confidence"], state["fraud_score"], state["sentiment"])
    state["decision"] = d
    state["final_decision"] = "AUTO_REFUNDED" if d == "AUTO_REFUND" else "PENDING"
    return state
```

### 5.4 设计要点

置信度路由是「证据链可信度」的第一道闸门：**证据不足时不进入自动决策**，从源头阻断「低质量证据 → 错误决策 → 错误退款」的链条。

## ⑥ 基于最小活跃任务数（Least Active）的人工工单派发算法

> 说明：当前 MVP 的「人工审批」是**公共待审批池**——任意主管可见全部 `SUSPENDED` 工单，无主动派单。本算法是 MVP 之上的**增强设计**，用于多名主管负载均衡，避免「忙的忙死、闲的闲死」。审批人角色为**主管**。

### 6.1 核心思想

将新产生的挂起工单派给**当前活跃任务数最少**的主管（Least Active），使主管间工作负载趋于均衡。

### 6.2 数据结构（Redis）

| Key | 类型 | 用途 |
| --- | --- | --- |
| `zset:sv:active_load` | ZSET | member=主管 ID，score=当前活跃工单数 |
| `claim:sv:{sv_id}:{ticket_id}` | String（SETNX） | 派单互斥标记，防重复派单 |
| `todo:sv:{sv_id}` | List | 该主管待办工单队列 |

### 6.3 派发流程

```text
工单进入 SUSPENDED
        │
        ▼
ZRANGE zset:sv:active_load 0 0 WITHSCORES   ← 取 score 最小（Least Active）的主管
        │
        ├─ 有主管 → SETNX claim 占位 → ZINCRBY +1 → LPUSH todo 队列
        │
        └─ 无主管 → 入公共待派池 pending:pool
```

### 6.4 原子性与竞态防护（Lua 脚本）

并发派单时，若「取最小 + 计数 + 记录」分步执行，可能出现两个派单器选中同一主管、重复计数。用 Lua 脚本原子化：

```lua
-- 原子派单：取最小活跃主管 + 计数 + 登记
local sv_id = redis.call('ZRANGE', KEYS[1], 0, 0)[1]   -- Least Active
if not sv_id then return nil end
local claimed = redis.call('SET', KEYS[2], sv_id, 'NX', 'EX', 60)
if claimed then
    redis.call('ZINCRBY', KEYS[1], 1, sv_id)
    redis.call('LPUSH', 'todo:sv:' .. sv_id, ARGV[1])   -- ARGV[1] = ticket_id
    redis.call('SET', 'assign:ticket:' .. ARGV[1], sv_id)
end
return sv_id
```

### 6.5 回收与均衡

| 事件 | 动作 |
| --- | --- |
| 主管审批完成 | `ZINCRBY zset:sv:active_load -1 sv_id` + 释放 `claim` |
| 主管超时未处理（如 30min） | 重新派发：先 `-1` 计数，再派给新的 Least Active |
| 主管下线/缩容 | 其 `todo:sv:{id}` 队列迁移回 `pending:pool` 重派 |

### 6.6 公平性平局处理

score 相同（多个主管活跃数相等）时，默认字典序会偏向固定主管。更公平的做法是维护 `last_assigned_at` 时间戳，平局取「最久未被派单」者；MVP 可用「字典序 + 轮询」近似。

```text
平局策略（增强）：
  score 相同 → 比较 last_assigned_at → 取最久未派者
  MVP 近似  → ZRANGE 字典序 + round-robin 轮询
```

# 第四部分 · 工程防御板块

## ⑦ 防资损幂等键的设计公式

### 7.1 资损风险场景

「退款」一旦重复执行即造成资损。以下场景会导致同一意图被重复处理：

- 网络超时后客户端重试（请求其实已成功）；
- 用户双击提交；
- 反向代理/网关重放请求。

若无幂等控制，每次重试都会新建工单 → 多张工单 → 多次退款 = **资损**。

### 7.2 幂等键设计公式

```text
① 客户端幂等键（client_key）：
   client_key = UUIDv4()
   —— 在「一次提交动作」的生命周期内生成并固定，重试必须复用同一 key，禁止每次请求重新生成

② 服务端复合键（redis_key / db 唯一键）：
   server_key = "{资源类型}:{操作主体}:{客户端幂等键}"
              = "idem:ticket:" + creator_id + ":" + client_key

③ 数据库兜底约束：
   UNIQUE(creator_id, idempotency_key)
```

### 7.3 三层防线

| 层 | 机制 | 作用 |
| --- | --- | --- |
| 第一层 | Redis `SET key value NX EX 86400` | 毫秒级拦截重复，首次抢到才建单 |
| 第二层 | DB 联合唯一索引 `UNIQUE(creator_id, idempotency_key)` | Redis 故障时的最终兜底，物理杜绝双写 |
| 第三层 | 重复请求返回原工单 ID | 幂等命中时回查并返回首次工单，不新建 |

### 7.4 关键设计要点

1. **key 稳定性**：幂等键必须在重试间稳定，这是幂等的核心前提。
2. **owner 隔离**：复合键含 `creator_id`，防止不同用户同名 key 互相污染。
3. **失败回滚**：若 Redis 抢到 key 但 DB 事务失败，必须删除/标记该 key，避免「键已占用但工单不存在」的悬空状态。

```python
def resolve_idempotency(redis, key: str, ticket_id: str) -> str | None:
    """SET NX：首次返回 None（应建单），重复返回已存工单 ID。"""
    if redis.set(key, ticket_id, nx=True, ex=86400):
        return None
    return redis.get(key)
```

## ⑧ 使用 Redis SETNX 实现分布式排他锁（防并发审批冲突）

### 8.1 问题场景

同一挂起工单可能被两名审批人（主管）同时提交审批。若不加锁，会出现两条审批记录、两次恢复执行，导致图被重复推进、状态错乱。

### 8.2 SETNX 原理

`SET key value NX PX <ms>` 是原子操作：**仅当 key 不存在时才写入并返回 OK**，天然实现「抢锁」。现代写法用 `SET ... NX PX`（`SETNX` 为旧命令，功能等价但无法同时设置过期时间，故推荐 `SET NX PX`）。

```text
锁 key  = lock:approve:{ticket_id}
锁 value = 随机 token（识别锁的持有者，防止误删他人锁）
锁 TTL  = 10s（PX 10000，防止持锁进程崩溃导致死锁）
```

### 8.3 加锁 / 释放协议

```text
加锁：
  SET lock:approve:{id} {random_token} NX PX 10000
   ├─ OK     → 抢锁成功，继续审批
   └─ nil    → 锁已被占，返回 409 冲突

释放（必须 Lua 原子比较 token 后删除）：
  if redis.call('GET', KEYS[1]) == ARGV[1] then
      return redis.call('DEL', KEYS[1])
  else
      return 0
  end
```

**释放为何必须用 Lua 比较 token**：若直接 `DEL`（无条件删除），当锁已过期、他人已抢到新锁时，会**误删他人的新锁**。比较 token 后删除，保证「只释放自己持有的锁」。

### 8.4 完整审批时序（锁 + 条件更新双保险）

```text
主管A                              Redis                        PostgreSQL
 │ SET lock:approve:t1 {tokA} NX PX 10000                          │
 │──────────────▶│ 返回 OK（抢锁成功）                              │
 │               │                                                 │
 │ 校验 t1.status == SUSPENDED                                     │
 │ 写 approval 记录 + 条件更新 status                               │
 │───────────────────────────────────────────────────────────────▶│
 │               │                                                 │
 │ XADD RESUME 消息                                                │
 │──────────────▶│                                                 │
 │               │                                                 │
 │ Lua 比较 tokA 后 DEL lock:approve:t1                            │
 │──────────────▶│ 释放锁                                          │
 │               │                                                 │
 │ 返回「恢复已入队」                                               │

主管B（并发）                                                     │
 │ SET lock:approve:t1 {tokB} NX PX 10000                          │
 │──────────────▶│ 返回 nil（锁被占）                               │
 │ 返回 409 Conflict  ← 不产生第二条审批记录                         │
```

### 8.5 双保险：锁 + 数据库条件更新

分布式锁只保证「同一时刻仅一个进程在审批」，但锁可能因 TTL 到期而失效。因此还需数据库**条件更新**兜底：

```sql
UPDATE tickets
SET status = 'RUNNING', decision = 'PENDING'
WHERE id = :id AND status = 'SUSPENDED' AND decision = 'PENDING'
-- 影响行数为 0 → 已被他人处理，返回 409
```

> 锁（互斥）+ 条件更新（状态机兜底）+ 可选 `UNIQUE(ticket_id)`（approvals 表）三层叠加，彻底杜绝并发审批冲突。

### 8.6 设计红线（对应三方对齐结论 A-01）

1. 锁值必须为**随机 token**，禁止固定值；
2. 释放必须**比较 token 后 Lua 删除**，禁止无条件 `DEL`；
3. 锁必须设 **TTL**，防止崩溃死锁；
4. 锁释放放在 `finally` 中，保证异常路径也释放。
