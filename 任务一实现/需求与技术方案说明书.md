## 2. 项目概述

### 2.1 背景与目标

客服处理客诉退赔时，需要人工判断凭证真伪、金额合理性以及舆情/欺诈风险，效率低且标准不一。本系统引入**多 Agent 协同**，用 LangGraph 编排 OCR、舆情风控、金额决策等智能体，在后台异步完成分析，给出"自动退赔"或"转主管人工审批"的结论，从而提升处理效率、统一决策标准，并保留完整审计轨迹。

### 2.2 核心目标

1. **自动化决策**：客服上传凭证提交工单后，系统自动执行 OCR → 风控 → 舆情 → 金额决策的完整链路。
2. **人工兜底**：对不确定或高风险工单，持久化中间状态并挂起，由主管审批后从断点恢复。
3. **安全可控**：JWT 认证 + RBAC 权限 + 请求幂等 + 分布式锁，避免越权和重复处理。
4. **可视化**：大屏实时展示 Agent 执行路径、OCR 文本、风险评分与审批入口。
5. **可部署可验证**：Docker Compose 一键启动，Locust 压测核心 API。

### 2.3 原始需求转述

- **用户与权限**：客服、主管登录，JWT 身份认证，不同角色拥有不同审批权限。
- **AI 决策流程**：提交审批请求后自动启动多 Agent 决策流（OCR、舆情风控、金额决策），基于 LangGraph 编排。
- **流程可中断**：决策流运行中可挂起（如等待人工补充材料），保存完整中间状态，恢复后从断点继续。
- **防重复提交**：前端每次提交携带唯一键；后端使用分布式锁保证同一请求不被重复处理。
- **可视化**：大屏可查看各 Agent 执行路径、OCR 识别文本和舆情风险评分。
- **可部署、可压测**：Docker Compose 一键启动，Locust 验证性能。

## 3. 需求说明

### 3.1 功能需求

| 编号 | 功能 | 说明 |
| --- | --- | --- |
| FR-01 | 登录认证 | 用户名 + 密码登录，返回 JWT Access Token |
| FR-02 | 角色权限 | 客服、主管两种角色，主管独占审批权限 |
| FR-03 | 工单创建 | 客服/主管提交金额、客诉描述与凭证图片，生成工单 |
| FR-04 | 凭证上传 | JPG/JPEG/PNG，单文件 ≤ 10MB，每单最多 3 张 |
| FR-05 | 多 Agent 决策流 | Intake → OCR → 风控 → 舆情 → 金额决策 →（人工审批） |
| FR-06 | 本地 OCR | PaddleOCR 本地推理，输出文字与置信度 |
| FR-07 | 风险与舆情分析 | 基于工单材料做欺诈打分（0–100）与舆情等级（LOW/MEDIUM/HIGH） |
| FR-08 | 金额决策 | 按确定性规则路由"自动退赔"或"人工审批" |
| FR-09 | 挂起与恢复 | 高风险/不确定工单中断并持久化上下文，主管审批后从断点恢复 |
| FR-10 | 防重复提交 | `X-Idempotency-Key` 幂等键 + Redis 锁 + 数据库唯一约束兜底 |
| FR-11 | 大屏展示 | 工单列表、Agent 流转图、OCR 结果、风险卡片、审批面板 |
| FR-12 | 实时更新 | SSE 推送 + 断线后每 2 秒轮询降级 |
| FR-13 | 审计轨迹 | 记录各节点输入/输出、审批人、审批意见、错误码 |

### 3.2 非功能需求

| 编号 | 类别 | 要求 |
| --- | --- | --- |
| NFR-01 | 性能 | 核心 API QPS ≥ 200，P95 < 300ms，错误率 < 0.1% |
| NFR-02 | 可用性 | 强杀 API/Worker 后，5 秒内按容器策略恢复 |
| NFR-03 | 一致性 | Redis 仅作队列/锁/checkpoint，业务事实以 PostgreSQL 为准 |
| NFR-04 | 可恢复性 | 挂起状态不因容器重启丢失，checkpoint 可持久化 |
| NFR-05 | 安全 | 密码哈希存储，密钥经环境变量注入，最小权限，审计脱敏 |
| NFR-06 | 可部署 | Docker Compose 一键启动 |
| NFR-07 | 可观测 | 预留监控指标接口（完整 Prometheus/Grafana 不在 MVP 内） |

### 3.3 角色与权限

| 角色 | 权限 |
| --- | --- |
| 客服（`CUSTOMER_SERVICE`） | 登录、创建工单、上传文件、查看本人列表/详情、查看本人事件流 |
| 主管（`SUPERVISOR`） | 客服全部能力 + 查看全部工单 + 审批 `SUSPENDED` 工单 |

> 数据权限必须在服务层过滤，不能仅靠前端隐藏按钮。

### 3.4 需求澄清结论

AI-A 提出的 10 个待澄清问题，本说明书给出的最终结论如下：

| AI-A 问题编号 | 待澄清项 | 最终结论 |
| --- | --- | --- |
| 1 | OCR 用真实服务还是 Mock | 本地 PaddleOCR 真实推理，输出文字与置信度 |
| 2 | 舆情风控数据源 | 仅基于工单材料，不抓取外网舆情；LLM 走可替换 OpenAI 兼容接口 |
| 3 | 金额决策逻辑 | 见 [7.2 决策规则](#72-决策规则)：金额 > 300 / OCR < 0.60 / 欺诈 ≥ 50 / 舆情非 LOW，任一满足即转人工 |
| 4 | 挂起触发条件 | 上述规则任一命中即进入 `HUMAN_REVIEW` 并挂起 |
| 5 | 谁恢复、是否二次鉴权 | 主管（`SUPERVISOR`）独占，审批接口 RBAC 校验 |
| 6 | 大屏轮询还是推送 | SSE 推送，断线降级为每 2 秒轮询 |
| 7 | 压测目标指标 | QPS ≥ 200、P95 < 300ms、错误率 < 0.1% |
| 8 | 完成状态是自动还是人工确认 | 低风险自动 `AUTO_REFUNDED`；高风险必须主管 `APPROVE`/`REJECT` |
| 9 | 是否多单并发 | 支持；Worker 可横向扩容，Redis 消费组并发消费 |
| 10 | JWT 过期与刷新 | 仅 Access Token，有效期 2 小时，无 Refresh Token |

## 4. MVP 范围边界

### 4.1 范围内

| 能力 | MVP 内容 |
| --- | --- |
| 用户与权限 | 客服、主管两种角色；用户名密码登录；JWT 鉴权；主管独占审批 |
| 工单 | 创建、本人/全量查询、详情查看、真实图片凭证上传 |
| 图片 | 仅 JPG/JPEG/PNG；单文件 ≤ 10MB；每单最多 3 张；不支持 PDF |
| Agent | Intake、OCR、风控、舆情、金额决策、HumanReview 人工节点 |
| OCR | 本地 PaddleOCR 推理，输出文字和置信度 |
| LLM | 可替换 OpenAI 兼容客户端调用云端 LLM，分析工单材料 |
| 流转 | `RUNNING → SUSPENDED → COMPLETED` 三态；挂起用 Redis Checkpointer 保存图上下文 |
| 决策 | 仅产生 `AUTO_REFUNDED`、`APPROVED`、`REJECTED`、`FAILED` 业务结果 |
| 实时性 | SSE 推送；断线每 2 秒轮询 |
| 部署压测 | Docker Compose；Locust 压测核心 API |

### 4.2 范围外（明确不做）

- 真实支付退款、账务、资金冻结、对账、支付回调与补偿（"退款"仅生成并持久化决策结果）；
- 外网爬虫、第三方舆情抓取、社媒检索、数据采购；
- PDF/视频/音频等复杂凭证处理；
- 组织、团队、队列分配、复杂数据权限；
- JWT Refresh Token、令牌黑名单、单点登录；
- 自动超时拒绝、邮件/短信提醒；
- 复杂多级审批、退回补料、人工工单派单；
- Prometheus/Grafana 完整监控大盘（可预留接口与指标）。

## 6. 核心设计原则

1. **API 短请求、Worker 长任务**：建单和审批接口只做校验、落库、投递消息，不能同步等待 OCR 或 LLM。
2. **业务事实与图内部状态分离**：PostgreSQL 保存可查询的业务结果与审计轨迹；Redis Checkpointer 只保存 LangGraph 可恢复上下文。
3. **先保守、后自动**：OCR 低置信度、LLM 超时、模型格式不合法等不确定情况一律不自动通过。
4. **决策规则可测试**：金额、风险、舆情的最终路由下沉为无 I/O 的纯函数，Agent 仅负责采集与归一化信息。
5. **幂等与互斥缺一不可**：创建防重使用幂等键；审批冲突使用单工单分布式锁；数据库状态更新再做条件约束。
6. **审计可回放**：关键节点、模型结果、审批人、审批意见和错误码须可查询，供大屏和问题排查复用。

## 7. 业务流程与状态机

### 7.1 三态与业务结果

| 流程状态 | 含义 | 可出现的业务结果 |
| --- | --- | --- |
| `RUNNING` | 已入队或 Worker 正在执行 Agent 图 | `PENDING` |
| `SUSPENDED` | 图在 HumanReview 节点中断，checkpoint 已保存 | `PENDING` |
| `COMPLETED` | 图已结束或处理不能继续 | `AUTO_REFUNDED`、`APPROVED`、`REJECTED`、`FAILED` |

> 失败语义通过 `COMPLETED + FAILED + error_code` 表达，既遵守三态，又保留失败原因。

### 7.2 决策规则

```text
IF amount > 300
   OR ocr_confidence < 0.60
   OR fraud_score >= 50
   OR sentiment != "LOW"
THEN HUMAN_REVIEW → SUSPENDED
ELSE AUTO_REFUND → COMPLETED + AUTO_REFUNDED
```

- `fraud_score` 为 0–100 整数，越高越可疑；
- `sentiment` 由工单材料风险分析得到（`LOW`/`MEDIUM`/`HIGH`），沿用需求中的"舆情风险"命名，不代表外网舆情监测；
- MVP 无自动拒绝条件，最终拒绝由主管在人工审批中作出；
- 任一模型超时、输出解析失败或 OCR 不可信，优先进入人工审批而非自动通过。

### 7.3 LangGraph 路径

```text
START
  → Intake
  → OCR
  → FraudRisk
  → SentimentRisk
  → AmountDecision
       ├─ AUTO_REFUND → 完成（AUTO_REFUNDED） → END
       └─ HUMAN_REVIEW → interrupt() → Redis Checkpoint
                                         ↓
                              主管 APPROVE / REJECT
                                         ↓
                         Command(resume=...) → 完成 → END
```

### 7.4 典型场景

#### 场景一：金额超限挂起后审批

1. 客服提交金额 `350.00` 和凭证图片，API 校验 JWT、幂等键、图片格式和大小。
2. API 创建 `RUNNING` 工单，写入 Redis Stream，立即返回 `202 Accepted`。
3. Worker 依次执行 Intake、OCR、风控、舆情和金额决策，写入 Agent 轨迹。
4. 金额超 300 元，决策为 `HUMAN_REVIEW`；HumanReview 调用 `interrupt()`。
5. Checkpointer 把线程状态保存到 Redis，工单更新为 `SUSPENDED`。
6. 主管提交 `APPROVE` 与意见；API 取得审批锁、校验状态，写审批记录和恢复任务。
7. Worker 消费恢复消息，用相同 `thread_id` 调用 `Command(resume={action: APPROVE})`。
8. 图完成，工单更新为 `COMPLETED + APPROVED`。

#### 场景二：低金额、低风险自动完成

1. 客服提交金额 `128.00` 和清晰凭证。
2. OCR 置信度 ≥ 0.60，风险分 20，舆情等级 LOW。
3. 决策节点输出 `AUTO_REFUND`，无需进入 HumanReview。
4. Worker 写入 `COMPLETED + AUTO_REFUNDED`，大屏展示全部节点成功。

| Agent | 输入 | 输出 | 失败处理 |
| --- | --- | --- | --- |
| Intake | 工单金额、图片清单、申请人 | 规范化基本字段 | 字段缺失：工单 `COMPLETED + FAILED` |

| HumanReview | `ticket_id`、提示信息 | `APPROVE/REJECT` | 等待主管；不自动超时 |

## 10. 关键技术设计

### 10.1 Redis Key 设计

| Key 模式 | 示例 | 用途 | TTL |
| --- | --- | --- | --- |
| `idem:ticket:{creator_id}:{key}` | `idem:ticket:u100:k-uuid` | 建单幂等记录，值为 `ticket_id` | 24 小时 |
| `lock:approval:{ticket_id}` | `lock:approval:t100` | 同工单审批互斥锁 | 10 秒，带唯一 token |
| `stream:ticket-jobs` | — | 初始执行与审批恢复消息队列 | 按运维策略保留 |
| `checkpoint:*` | LangGraph 管理 | 挂起图的状态与历史 | 与挂起工单保留策略一致 |
| `event:ticket:{ticket_id}` | 可选 | SSE 轻量通知通道 | 短 TTL 或 Pub/Sub |

### 10.2 幂等设计（创建工单）

1. 前端在一次用户点击生命周期中生成 UUID，置于 `X-Idempotency-Key`；重试必须复用同一 key。
2. API 校验 key 格式与长度后，以 `creator_id + key` 组成 Redis key，执行 `SET value NX EX 86400`。
3. 首次抢到 key 后创建数据库工单；若数据库事务失败，需删除/标记该 Redis key，避免"键已占用但工单不存在"。
4. 重复请求直接返回首次工单 ID 与当前状态。
5. PostgreSQL 联合唯一索引提供 Redis 异常场景下的最终兜底。

### 10.3 分布式锁（审批）

1. 主管请求以 `SET lock:approval:{ticket_id} {random_token} NX PX 10000` 取锁。
2. 必须用"比较 token 后删除"的 Lua 脚本释放锁，禁止无条件 `DEL`，避免误删他人的新锁。
3. 数据库以条件更新约束状态：`WHERE id=? AND status='SUSPENDED' AND outcome='PENDING'`。
4. 更新成功后写审批记录、投递恢复 Stream 消息；再次审批返回 `409 Conflict`。

### 10.4 Redis Streams 消息格式

新建工单消息：

```json
{
  "type": "START",
  "ticket_id": "t_123",
  "thread_id": "lg_t_123",
  "created_at": "2026-08-17T10:00:00Z"
}
```

审批恢复消息：

```json
{
  "type": "RESUME",
  "ticket_id": "t_123",
  "thread_id": "lg_t_123",
  "approval_action": "APPROVE",
  "approval_id": "a_456"
}
```

Worker 使用消费组：

- 成功完整处理后才 `XACK`；
- 处理异常不直接确认，保留 Pending Entry 供重试/回收；
- 不可恢复错误更新为 `COMPLETED + FAILED`、记录 `error_code` 后再确认；
- 开发/演示环境单 Worker，压测/生产可横向扩容。

### 10.5 LangGraph 挂起与恢复约束

- 每个工单生成并持久化唯一 `thread_id`；
- 初始执行与恢复执行必须使用**同一 Redis Checkpointer 和同一 `thread_id`**；
- HumanReview 通过 `interrupt()` 产生中断，不手工 `pickle` 图对象；
- API 不能直接调用 `graph.resume()`，而是写入 `RESUME` 消息，由 Worker 串行恢复，避免 API 与 Worker 争抢图状态；
- checkpoint 缺失时，工单置为 `COMPLETED + FAILED`，错误码 `CHECKPOINT_NOT_FOUND`，并保留审计记录。

## 12. 大屏展示与实时更新

### 12.1 页面最小组成

| 区域 | 内容 | 数据来源 |
| --- | --- | --- |
| 工单列表 | 工单号、金额、状态、最终结果、风险分、创建时间 | `GET /api/tickets` |
| 工单摘要 | 客诉描述、上传图片、当前状态、最终结果/错误信息 | `GET /api/tickets/{id}` |
| Agent 流转图 | Intake → OCR → 风控 → 舆情 → 决策 → HumanReview 的节点状态 | `agent_traces` |
| OCR 卡片 | 聚合文字、平均/最低置信度、低置信度提示 | `tickets.ocr_*` + OCR 轨迹 |
| 风险卡片 | 欺诈分、舆情等级、触发人工审核原因 | `tickets.fraud_score`、`tickets.sentiment`、决策轨迹 |
| 人工审批面板 | 仅当工单 `SUSPENDED` 且当前用户为主管时展示 | 工单状态 + JWT role |

### 12.2 实时更新机制

1. Worker 每完成一个节点或状态切换，先写 `agent_traces`/`tickets`，再发布轻量事件。
2. SSE 只推送事件提醒，如 `trace_updated`、`ticket_status_changed`、`completed`。
3. 前端收到事件后调用详情接口获取完整可信数据；不以 SSE 内容作为最终业务事实。
4. SSE 断开后前端每 2 秒轮询详情；工单进入 `COMPLETED` 后停止轮询。
5. 轨迹节点状态统一为：`PENDING`（灰）、`RUNNING`（蓝）、`SUCCESS`（绿）、`SUSPENDED`（黄）、`FAILED`（红）；必须显示文本或图标，不能仅用颜色传达状态。

## 13. 异常、边界与安全策略

### 13.1 必须覆盖的业务边界

| 条件 | 系统处理 |
| --- | --- |
| 同一客服重复提交相同 `X-Idempotency-Key` | 返回首次工单，不创建第二条记录、不重复入队 |
| 两名主管同时审批同一挂起工单 | 首位取得锁并完成条件更新；另一位收到 `409` |
| 非主管调用审批接口 | `403 FORBIDDEN` |
| 客服请求非本人详情 | `403` 或按安全策略返回 `404` |
| 上传超过 3 张或任意图片 >10MB | 拒绝请求，不保存文件 |
| 文件 MIME 或文件头不匹配图片格式 | 拒绝请求；不可仅信任浏览器 Content-Type |
| OCR 无结果或置信度 <0.60 | 记录 OCR 结果，强制人工审核 |
| 云端 LLM 超时、5xx、限流 | 有限重试（建议 1 次、指数退避）；仍失败按保守值进入人工审批 |
| LLM 非法 JSON/非法等级 | 结构化解析失败后有限重试；仍失败进入人工审批 |
| Redis Stream 消息重复投递 | Worker 以工单状态和 thread_id 判断，不重复推进已完成工单 |
| checkpoint 缺失 | `COMPLETED + FAILED`，记录 `CHECKPOINT_NOT_FOUND` |
| Worker 执行不可恢复异常 | 写 `FAILED` 结果和错误码；消息在完成状态落库后确认 |
| 审批已成功但恢复消息投递失败 | 记录待投递事件/失败日志并重试；建议采用 outbox 模式，至少保证可人工补偿 |

### 13.2 安全最小要求

- 密码采用 bcrypt 或 Argon2 哈希，禁止明文、可逆加密或日志输出；
- `JWT_SECRET`、数据库密码、LLM Key 仅经环境变量/Secret 注入，禁止提交仓库；
- 开发环境默认账号仅用于演示，生产须经初始化脚本或管理员创建；
- 文件名服务端重新命名；上传目录禁止执行权限；下载/预览需重新校验访问权限；
- LLM 提示词须明确"仅输出规定 JSON/枚举值"，并用 Pydantic 校验模型输出；
- OCR 文本、用户输入不得拼接为系统指令，需标记为不可信材料；
- 审批意见和 OCR 文本按长度限制保存，避免日志/大屏被超长内容拖垮；
- 审计日志不得保存 Authorization Header、密码或 LLM API Key。

## 14. 部署、压测与验收

### 14.1 Docker Compose 服务编排

| 服务 | 容器职责 | 健康检查 |
| --- | --- | --- |
| `frontend` | Nginx 托管 React 构建产物，反向代理 `/api` | HTTP 首页返回 200 |
| `api` | FastAPI API | `/healthz`、`/readyz` |
| `worker` | Redis Streams 消费者与 LangGraph 执行器 | 进程存活 + Redis 连通性 |
| `postgres` | PostgreSQL 业务数据 | `pg_isready` |
| `redis` | Stream、锁、幂等、checkpoint | `redis-cli ping` |

持久化卷建议：

- `postgres_data`：数据库数据；
- `uploads_data`：MVP 本地凭证文件；
- Redis 开启 AOF 持久化，确保挂起 checkpoint 不因容器重启丢失。

`api` 和 `worker` 使用 `restart: unless-stopped` 或等效策略并配置健康检查。强杀 API 或 Worker 后，应在 5 秒内恢复进程服务能力，验收时记录测试证据。

### 14.2 Locust 压测口径

压测对象是**短时核心 API**，而非云端 LLM 完整完成时长：

- 登录：`POST /api/auth/login`
- 建单：`POST /api/tickets`
- 工单列表：`GET /api/tickets`
- 工单详情：`GET /api/tickets/{id}`
- 审批入队：`POST /api/tickets/{id}/approval`（预置挂起工单）

验收基线：

| 指标 | 标准 |
| --- | --- |
| QPS | ≥ 200 |
| P95 延迟 | < 300ms |
| 错误率 | < 0.1% |
| 稳定性 | API、Worker、PostgreSQL、Redis 无 OOM、死锁、反复重启 |

注意事项：

- LLM/OCR 任务由 Worker 异步执行，建单接口只确认"已受理"，不能把外部模型耗时混入核心 API P95；
- 压测环境可将 Worker 模型调用替换为固定延迟 Stub，但报告须明确区分"API 性能"与"真实 AI 推理时延"；
- 压测必须使用独立数据集/幂等键，避免大量重复命中幂等缓存造成虚高；
- 报告记录宿主机 CPU、内存、容器资源限制、并发用户数、加压速率、持续时间和原始 Locust 输出。

### 14.3 最小验收用例

| 编号 | 用例 | 预期结果 |
| --- | --- | --- |
| E2E-01 | 350 元 + 清晰图片 + 低风险 | 工单进入 `SUSPENDED`；主管审批后进入 `COMPLETED + APPROVED` |
| E2E-02 | 128 元 + OCR≥0.60 + 风险20 + LOW | 直接进入 `COMPLETED + AUTO_REFUNDED` |
| E2E-03 | OCR 置信度低 | 强制进入 `SUSPENDED` |
| E2E-04 | 相同幂等键并发/重复建单 | 返回相同工单，数据库仅一条 |
| E2E-05 | 两主管并发审批 | 仅一条审批有效；另一条得到 `409` |
| E2E-06 | 客服审批/越权读单 | 返回 `403` 或安全的 `404` |
| E2E-07 | LLM 超时/格式错误 | 不自动通过，保守进入人工审批 |
| E2E-08 | Worker/API 容器强杀 | 5 秒内按容器策略恢复；未完成消息可继续处理或被标记失败 |

## 结论

本方案以**异步解耦、可恢复状态机、保守自动化、可审计决策**为核心，满足原始需求中的用户鉴权、多 Agent 协作、三态流转、Redis 挂起恢复、请求防重、大屏展示、Docker Compose 与 Locust 压测要求。

实现红线：

1. 不能在 API 请求中同步执行 OCR 或 LLM；
2. 不能把 Redis 当作工单业务事实的唯一来源；
3. 不能用无 token 的 `DEL` 释放分布式锁；
4. 不能让异常或模型不确定性触发自动通过；
5. 不能绕过 Worker 由 API 直接恢复 LangGraph；
6. 不能将"记录退款决策"误实现为"调用真实支付退款"。
