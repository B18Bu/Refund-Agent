# 工单 6 安全治理中心与未完成项补足设计

**日期：** 2026-09-01  
**状态：** 已完成交互设计确认，待审阅实施规格  
**范围：** 工单 6 未完成的安全治理能力，以及其在退赔决策控制台中的主管侧可视化。

## 1. 背景与问题

当前项目已具备基于规则的 DLP、Critic 注入检测、命中后转人工、红蓝报告与代码审计报告。前端已在工单详情展示单笔“安全校验”，但以下能力尚未形成完整治理闭环，也没有主管总览入口：

1. 动作层政策校验未覆盖未来真实 Tool 调用与支付动作参数。
2. DLP 只有正则规则；未实现 NER 增强，也没有足以支撑“准确率 ≥99%”的验证集。
3. 红蓝测试是本地、顺序的规则引擎批测，不是 API 与 Worker 的并发端到端演练，且攻击样本不足 100 条。
4. `SECURITY_LLM_ENHANCE` 尚未实现；若引入，仅能作为不影响确定性决策的辅助解释，不能参与路由、放行或重试。
5. 安全审计、红蓝报告与 DLP 统计以 Markdown 保存，未产品化为受 RBAC 保护的治理指标与审计入口。

## 2. 目标与非目标

### 目标

- 新增仅主管可见的一级导航“安全治理中心”，成为工单 6 安全能力的统一入口。
- 以明确的数据口径展示：运行时安全事件、最近一次红蓝测试、DLP 验证状态、代码安全审计和待补足项。
- 为工单 6 的缺口建立分期实施和验收边界；所有会改变自动退赔资格的判断保持确定性。
- 安全页面与接口不返回 OCR 原文、脱敏前 PII、Token、密钥、提示词全文或可用于绕过防护的规则细节。

### 非目标

- 不新增角色、不修改 JWT/RBAC 协议、审批锁、Redis 幂等键或数据库迁移策略。
- 不调用真实支付接口；`AUTO_REFUNDED` 仍然只是确定性决策记录。
- 不将 LLM 用于路由、动作放行、重试或确定性数据转换。
- 首期不引入沙箱执行能力；后续若涉及沙箱，必须按项目护栏独立设计与验收。

## 3. 信息架构与权限

### 导航

在主管侧边栏“Agent 评测”之后增加一级菜单项：

`安全治理中心`（Shield 图标）→ `/security-governance`

客服角色不渲染该菜单。直接访问该路由时，前端重定向到“我的申请”；后端全部治理接口使用 `require_role(Role.SV)`，不能仅依赖前端隐藏。

### 首页布局

页面采用已经确认的控制台布局：

1. 标题区：页面标题、运行/报告口径提示、手动刷新。
2. 指标区：安全拦截率、合法样本误拦截率、DLP 漏报率、待人工复核安全事件数。
3. 防护效果区：按攻击类别的最近一次红蓝测试拦截率，以及治理检查状态。
4. 审计事件区：最近安全事件的时间、事件类型、脱敏摘要与处置状态。
5. 待补足项必须始终可见，不能因旧报告指标达标而被误呈现为工单全部完成。

所有图表提供文字数值后备、错误重试、加载态和窄屏单列布局；页面导航、刷新与审计行都必须可键盘访问并保留可见焦点。

## 4. 数据口径与接口设计

### 数据来源

- **运行时事件：** 从已落库的工单 `evidence_audit.security`、决策原因、状态与创建时间聚合。事件摘要只显示规则类别、风险等级、转人工结果和脱敏工单标识，不返回 OCR 文本。
- **红蓝测试：** 从每次评测生成的结构化结果读取。现有 Markdown 报告仅作为历史证据；实施时，`run_red_blue_test.py` 必须额外输出带生成时间、样本量、分类统计、失败明细计数的 JSON 结果，前端不得解析 Markdown。
- **DLP 验证：** 显示最近验证集的样本量、漏报数、误报数和结论；样本量不足验收门槛时，状态为“待补足”，不显示“准确率 ≥99%”。
- **代码审计：** 仅显示审计时间、结论和发现级别汇总；完整报告保留在受控文档中。

### 接口

新增主管接口 `GET /api/security-governance/summary`，返回以下经脱敏的数据：

```text
generated_at
runtime: { pending_human_review, recent_events[] }
red_blue: { available, generated_at, total_count, attack_count, legitimate_count,
            block_rate, jailbreak_defense_rate, false_positive_rate, categories[] }
dlp: { available, generated_at, sample_count, missed_count, false_positive_count,
       accuracy, acceptance_status }
audit: { available, generated_at, status, finding_counts }
gaps: [{ key, title, description, status }]
```

接口错误时返回标准 HTTP 错误；缺少某类报告时返回 `available: false` 与“报告暂不可用”，不可用 `0` 或模拟数值伪造正常状态。接口不得读取或输出原始上传文件、原始 OCR、密钥、提示词全文。

## 5. 工单 6 缺口补足的实施顺序

### 阶段一：治理数据产品化与页面入口

- 定义结构化红蓝、DLP、代码审计结果文件与读取层。
- 新增主管接口、`SecurityGovernance` 页面、受限路由、侧栏菜单与前端类型。
- 通过页面清晰显示“已验证能力”和“待补足能力”，先完成可审计、不可误导的可见性。

**验收：** 客服不能访问路由/API；主管能看到实时事件和最近报告；缺失报告不被伪装为通过；前端构建及现有页面回归通过。

### 阶段二：动作层统一治理

- 在进入任何 Agent、Tool 或未来支付动作前，加入统一的确定性 `ActionPolicy` 校验。
- 校验对象包含不可信输入、Tool 名称和结构化参数；支付相关动作默认拒绝，除非由系统固定动作白名单、RBAC、审批状态和决策条件共同满足。
- 审批、幂等、条件更新和审批锁继续是下游不可绕过的防线；策略层不能替代它们。

**验收：** 危险 Tool/参数即使不在 OCR 文本中也会被拒绝或转人工；合法流程不改变 128 元订单的既有确定性判断；测试证明策略不能触发真实支付。

### 阶段三：NER 增强 DLP 与质量验证

- 在正则规则之后增加可配置的 NER 实体识别适配层；依赖不可用或识别失败时，保留正则 DLP 并显式记录降级状态。
- 建立版本化、脱敏的 PII 验证集，覆盖手机号、身份证、银行卡、邮箱、API Key，以及 NER 可识别的中文姓名/地址等新增实体。
- 通过测试与脚本计算 Precision、Recall、漏报和误报；不足验收标准时前端明确显示“未达标”。

**验收：** 预先定义且足量的测试集上脱敏准确率 ≥99%，不泄露样本明文到日志或报告。

### 阶段四：端到端并发红蓝演练

- 扩充为至少 100 条攻击 Payload，另保留合法对照样本；覆盖注入、越狱、编码绕过、多语言、系统提示篡改和危险 Tool 参数。
- 通过 FastAPI 与 Worker 的真实队列路径并发执行，使用 `asyncio.gather(..., return_exceptions=True)` 收集结果；单个样本失败不得取消其余样本。
- 报告聚合 API/Worker 错误码、队列失败、转人工结果与类别拦截率，生成结构化文件并保留失败样本的脱敏摘要。

**验收：** 攻击样本 ≥100；注入拦截率 ≥95%，越狱防御成功率 ≥98%；失败报告显示真实差距而非写作“通过”。

### 阶段五：可选 LLM Critic 辅助评分

- 仅在 `SECURITY_LLM_ENHANCE=true` 时调用；输入必须先 DLP 脱敏。
- 其结果只能作为解释性审计字段或人工复核建议；规则引擎、审批状态、Tool 策略和决策规则是唯一可执行依据。
- LLM 超时、异常、解析错误均记录为治理遥测，且不阻塞主事件循环、不改变原有规则结论。

**验收：** 关闭开关时行为不变；任何 LLM 输出均不能使被规则拦截的动作放行；遥测无原始 PII。

## 6. 错误处理与安全约束

- 页面数据加载失败时显示可重试错误，不影响退赔与审批流程。
- 报告文件缺失、解析失败或内容过期时显示“暂不可用/已过期”，并记录安全运维事件；不回退到模拟数据。
- 前端不做权限裁决；路由保护只改善体验，后端角色校验是最终边界。
- 页面、接口、日志、报告和追踪只传掩码文本或聚合统计，禁止输出密码、Token、API Key、原始图片、原始 OCR 与攻击 Payload 原文。

## 7. 测试设计

先为每项新增行为编写失败测试并确认因功能缺失失败，再编写最小实现：

1. 后端：客服请求治理接口返回 403；主管接口仅返回允许字段；报告缺失状态准确；运行事件不会泄露 OCR/PII。
2. 前端：主管可见导航与路由；客服不能访问；加载失败可重试；数据口径与“待补足”状态可见；图表存在文字数据后备和键盘焦点。
3. 安全：动作层策略拒绝危险 Tool 与参数；NER 降级不会放行 PII；并发红蓝执行中单样本异常不取消其他测试。
4. 回归：`pytest backend/tests -q`、Golden Dataset、红蓝演练、前端测试与 `npm run build` 均通过；验证输出必须保存到证据目录。

## 8. 成功标准

- 主管能够在一个可信、可追溯且不泄露敏感材料的页面中识别安全风险、验证来源和待办缺口。
- 客服既没有导航入口，也不能从接口或直接 URL 获取治理数据。
- 工单 6 的每个未完成项都有明确实现边界、失败态和可验证验收条件。
- 所有自动退赔仍严格受现有金额、OCR、欺诈、舆情、安全红线、审批锁与确定性规则约束。
