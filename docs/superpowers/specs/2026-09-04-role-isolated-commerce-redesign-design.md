# 角色隔离电商平台与退赔决策联动设计

## 1. 目标与范围

将现有项目改造为同一 React/FastAPI 应用内的三角色平台：普通用户进入消费者商城；客服仅处理退款审核；主管负责审批、监控与治理。商城目录必须由 vivo、OPPO 等品牌官网的固定公开 HTML 或 JSON 接口真实初始化，不能展示伪造商品。

本期不提供用户注册、改密、真实支付、真实资金退款、库存扣减、物流或优惠券功能。

## 2. 角色、预置账号与路由

| 角色 | 预置账号 | 登录后首页 | 允许功能 | 禁止功能 |
|---|---|---|---|---|
| `CUSTOMER` | `customer_01 / secret123` | `/shop` | 浏览、购物车、地址、下单、模拟支付、查看自己的订单、发起/查看退款 | 客服队列、主管审批、监控、治理 |
| `CS` | `customer_service_01 / secret123` | `/service/refunds` | 查看待人工退款、抢占并处理退款 | 商城、购物车、个人下单 |
| `SV` | `supervisor_01 / secret123` | `/monitor` | 查看/审批退款、监控、治理 | 商城、购物车、个人下单 |

登录页保留账号密码表单，增加三组快捷填充按钮。JWT 必须携带角色；前端路由守卫只用于体验，后端每个接口必须基于 JWT/RBAC 再次校验。新增 `CUSTOMER` 不改变既有 `CS`、`SV` 的审批锁、条件更新和数据访问约束。

## 3. 前端信息架构

### 3.1 消费者商城

消费者使用独立 `CustomerShell`，仅有“商城、购物车、订单、退款”导航。视觉采用浅色现代品牌商城：顶部搜索与购物车入口、品牌筛选、商品大图卡片、加载/错误/空状态，以及移动优先的响应式布局。

商城首页依次展示：品牌入口、`≤300 元` 低价专区、`301–3000 元` 中价专区、`>3000 元` 高价专区。商品详情可选择规格和数量；价格、可售状态与订单金额必须来自后端，不信任前端计算。每个可交互控件有可见文本或 ARIA 标签，保留键盘焦点和失败重试入口。

### 3.2 客服与主管后台

`CS` 与 `SV` 使用 `BackofficeShell`，不出现商城、购物车或下单导航。客服首页是退款队列，展示订单快照、退款原因、凭证、金额及确定性风控摘要；主管保留现有监控、审批与治理页面。自动退赔记录只读，人工退款使用既有审批锁抢占，未抢到锁时返回明确冲突状态。

## 4. 商品目录与首次初始化

### 4.1 固定来源与安全边界

适配器只允许调用代码配置的 vivo、OPPO 官网公开端点，可用 HTML 或 JSON 接口。请求不接受用户 URL；固定超时、每来源串行限速、HTTPS 校验和响应字段校验继续生效。网页返回内容是不可信数据，不能生成新工具权限或执行脚本。

### 4.2 首次成功门槛

Docker 启动时运行目录初始化。只有同一次成功结果满足以下条件才把目录标记为可用：

- vivo 至少 20 个可售 SKU；
- OPPO 至少 20 个可售 SKU；
- 每个品牌至少 1 个价格 `≤300 元` SKU；
- 整个目录同时存在 `≤300 元`、`301–3000 元`、`>3000 元` 商品。

不满足时状态为 `INITIALIZATION_FAILED`，商城显示初始化失败及重试说明，不展示伪造商品，也不允许加购或下单。成功时持久化产品、规格、价格、图片 URL、来源、抓取时间与本次运行摘要。

后续每日抓取仅在新的完整结果通过同一门槛后替换可用缓存；失败或不完整结果保留最近一次成功缓存，同时记录错误码与原因。没有任何成功缓存时不得降级为宿主机数据或静态演示商品。

## 5. 订单、退款与决策流

下单后模拟支付立即成功，不进入客服订单审核。用户退款必须填写原因；商城表单要求至少上传 1 张商品/问题凭证。为兼容已有 API，后端仍接受“仅原因、无凭证”的申请，但该申请必定进入人工审核，不得自动退赔。有凭证时进入现有 OCR、欺诈、舆情、金额决策链。退款凭证在 API 层使用现有文件数量、大小、隔离存储校验，不能只接受任意路径字符串。

金额 `≤300 元` 且 OCR 置信度、欺诈分数、舆情红线及其他确定性规则均满足时，决策为 `AUTO_REFUNDED`；这只改变模拟业务状态，不调用真实支付。其他申请进入人工审批。退单状态仍由 `map_ticket_to_return_status` 确定性映射，LLM 不参与路由、重试或最终状态映射。

客服与主管同时处理同一人工退款时，沿用 Redis 审批锁与数据库 `SUSPENDED` 条件更新：仅一方成功抢占；另一方得到 `409` 与“申请正在处理中”，不得重复提交审批结果。

## 6. 服务端接口与隔离

- 商品目录读接口在目录可用后可公开访问；地址、购物车、订单、退款写入及用户订单查询仅允许 `CUSTOMER` 且只能访问当前用户自己的记录。
- 客服队列接口仅允许 `CS`、`SV`：只返回人工退款；客服不能调用商城写接口。
- 主管接口继续使用既有 `SV` 审批及治理 RBAC。
- Ticket 详情向后台返回最小订单摘要（订单号、商品名、退款原因），但普通用户不读取内部 OCR、欺诈、舆情、锁或审批人信息。

新增字段和状态采用显式 SQL 迁移，兼容已有生产数据库；禁止通过 `create_all` 静默扩展既有表结构。

## 7. 调度与运行

Compose 增加独立目录初始化/调度 Worker，API 不在用户请求链路抓取网络商品。启动依赖：PostgreSQL、Redis 健康后先运行初始化；目录状态成功才开放商城可售接口。每日计划由配置控制，失败不阻塞 API 主事件循环或现有退款 Worker。

## 8. 验收与测试

- 登录快捷填充、三角色登录定向与跨角色路由/API 拒绝测试。
- 首次抓取门槛：数量、各品牌低价 SKU、三个价格区间缺一即失败。
- 首次成功缓存、后续抓取失败回退、无缓存不展示商品测试。
- 用户订单/购物车/退款隔离；客服与主管不得访问商城写操作测试。
- 无凭证退款必定转人工；有凭证且 `≤300 元` 且所有低风险条件满足才自动退赔测试。
- 客服/主管并发审批只有一个成功、另一个返回冲突测试。
- 前端构建、移动端布局与消费者/后台导航快照测试。
- Docker 首次初始化、后端全量测试、前端构建和 HTTP 健康检查通过。

## 9. 实施顺序

1. 角色枚举、JWT、预置账号与 RBAC 契约。
2. 目录初始化状态、固定来源适配器与缓存门槛。
3. 消费者/后台壳层、登录快捷入口及商城 UI。
4. 客服退款队列、凭证上传与角色隔离。
5. 调度容器、端到端测试、Docker 验收与视觉原型验证。
