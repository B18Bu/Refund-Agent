# 客诉舆情退赔决策系统：STAR 社招面试讲义

> **使用说明：** 本讲义基于当前仓库实现整理，适用于后端、全栈或 AI 应用工程师社招技术面。回答时应按个人实际负责范围调整「我主导」或「我参与」的表述，不要把团队成果全部表述为个人贡献。
>
> 文中的 OCR、端到端、并发审批和 Locust 数据均来自仓库中的历史验证报告，并非本讲义编写时重新执行得到的结果。

## 1. 30 秒项目简介

这是一个面向电商客诉退款场景的多 Agent 辅助决策系统。客服提交退款金额和凭证图片后，系统异步完成本地 OCR、欺诈风险分析、舆情分析和确定性决策。低风险工单自动退赔；金额较高、证据不充分或风险较高的工单会挂起，由主管审批后从原来的决策断点恢复。

项目的核心价值不是「调用了多个模型」，而是把模型的不确定性放进一个可审计、可恢复、可并发控制的退款流程中，优先避免错误自动退款造成资金损失。

## 2. 90 秒完整口述版本

> 这个项目解决的是传统退款流程规则单一、人工审核效率低、风险场景难以兼顾的问题。只按金额或订单状态判断，无法利用凭证图片、欺诈风险和负面舆情等信号；如果把所有工单都交给人工，又会影响低风险退款的时效。
>
> 我的目标是实现一条「低风险自动处理、高风险人工兜底」的异步决策链，同时保证审批能够恢复、重复请求不会重复建单、多个主管并发审批不会造成重复退款。
>
> 在实现上，我用 FastAPI 提供鉴权、工单、文件和审批 API，用 Redis Streams 将请求接入与耗时分析解耦，再由 Worker 执行 LangGraph 决策图。图中依次完成 OCR、欺诈和舆情分析，最后由纯函数决策规则决定自动退款还是进入人工审批。人工节点使用 LangGraph 原生 `interrupt()` 挂起，状态由 PostgreSQL Checkpointer 保存，审批后通过 `Command(resume)` 继续执行。针对资金风险，我还加入了建单幂等、随机令牌加 Lua 脚本的审批锁，以及数据库状态条件更新三层控制。
>
> 仓库历史验证记录显示：低风险 128 元工单可以自动退赔；350 元工单可以挂起、审批并恢复完成；6 线程并发审批只有 1 个请求成功、其余返回冲突。针对短 API 的 Locust 压测，历史记录达到约 190～215 QPS、P95 小于 300 ms、错误率为 0%。

## 3. 业务问题与端到端方案

```text
客服提交金额与凭证
        ↓
FastAPI 鉴权、参数校验、幂等控制、持久化
        ↓  XADD
Redis Streams 异步队列
        ↓  XREADGROUP
Worker + LangGraph
Intake → OCR → 欺诈分析 → 舆情分析 → 决策
        ↓                         ↓
自动退款并完成              人工节点 interrupt() 挂起
                                      ↓
                              主管审批 → RESUME 消息
                                      ↓
                              从 Checkpoint 恢复并完成
```

这条链路将「同步 API 响应」与「OCR、LLM 等慢任务」分开：API 只负责可靠接单，Worker 负责耗时决策。这样既避免用户长时间等待，也使 Worker 能独立扩容和失败重试。

## 4. 模块、实现与所解决的问题

| 模块 | 关键实现 | 解决的问题 | 面试表达重点 |
| --- | --- | --- | --- |
| API 与认证 | FastAPI、JWT、bcrypt、客服/主管 RBAC | 防止未授权访问与客服越权审批 | API 层负责身份和权限，业务流转交给 Worker，职责不混杂。 |
| 工单创建与文件 | `POST /api/tickets/with-files` 先保存图片再入队；单独上传接口限制图片数量 | 避免先入队、后上传导致 Worker OCR 到空凭证 | 文件就绪后才发送 START 消息，保证异步消费者读取到完整输入。 |
| 异步任务队列 | Redis Streams 的 `XADD`、消费者组 `XREADGROUP`、成功后 `XACK` | OCR 与风险分析耗时，不能阻塞 HTTP 请求；需要可消费、可确认的任务通道 | API 是生产者，Worker 是消费者，可分别扩容。 |
| Agent 编排 | LangGraph：Intake → OCR → Fraud → Sentiment → Decision → HumanReview | 多步骤决策容易在代码中演变成难维护的嵌套条件和状态耦合 | 图只描述步骤与路由；节点只完成能力调用和状态组装。 |
| OCR | 本地 PaddleOCR；多张图取最低置信度；无图或识别失败为 0 | 凭证信息无法直接被规则或风险模型使用；多图中存在低质量图片 | 用「木桶原则」处理证据质量，任一凭证不可靠就不自动放款。 |
| 风控与舆情 | OpenAI 兼容 LLM 适配器，可切换 DeepSeek 或本地 Mock | 模型服务不稳定、输出不规范时不能误放款 | 模型异常按高风险处理，体现「宁挂勿错退」而不是盲目自动化。 |
| 决策规则 | `decide(amount, ocr_confidence, fraud_score, sentiment)` 纯函数 | 关键资金规则散落在节点中，难以测试和审计 | 将金额、OCR、欺诈和舆情阈值集中为唯一决策来源，边界可单测。 |
| 人工审批恢复 | `interrupt()`、PostgreSQL Checkpointer、`Command(resume)` | 高风险工单需要等待人工，不能丢失中间结果，也不能从头重跑 | 使用框架原生暂停/恢复，避免手工序列化图状态。 |
| 幂等控制 | `X-Idempotency-Key` + Redis `SET NX` + 24 小时 TTL | 网络重试或用户重复点击导致重复创建退款申请 | 首次写入业务标识，后续同键请求返回同一工单，而不是重复入队。 |
| 审批并发控制 | 随机 token 锁、Lua 比较后删除、`status='SUSPENDED'` 的数据库条件更新 | 两个主管同时审批同一工单可能造成重复处理和资损 | Redis 锁降低竞争，数据库原子条件更新作为最终防线。 |
| 审计与事件 | `agent_traces`、失败错误码、Redis Pub/Sub 事件、详情页流转图 | 出现异常后无法解释「哪个环节、因为什么失败」 | 保存节点轨迹、中间风险结果和错误信息，支撑排障和人工决策。 |
| 前端控制台 | React、角色化路由、工作台、详情、审批页、监控页和大屏 | 客服、主管所需视图不同；审批人需要快速理解上下文 | 客服只看个人工单，主管看优先队列和完整决策证据。 |
| 部署与验证 | Docker Compose、PostgreSQL、Redis、API、Worker、Nginx 前端；pytest、E2E、Locust | 本地能运行不代表可交付；并发与异步问题不能只靠单测覆盖 | 用容器化和分层测试验证真实链路，而非只展示代码。 |

## 5. 可重点展开的 STAR 案例

### 案例一：把同步退款判断改造成可恢复的异步审批流

- **S（背景）：** 简单的同步规则无法同时处理图片凭证、风险信号和人工复核。OCR 与 LLM 调用耗时且可能失败，如果请求线程一直等待，用户体验和服务吞吐都会受影响。
- **T（任务）：** 实现低风险自动退款、高风险人工审批，并在审批后延续原决策上下文，而不是重新计算或手工拼接状态。
- **A（行动）：** 用 Redis Streams 解耦 API 和 Worker；在 LangGraph 中声明固定节点与条件路由；将人工节点实现为 `interrupt()`；默认使用 PostgreSQL Checkpointer 保存图状态，审批接口只写入 RESUME 消息，最终由 Worker 调用 `Command(resume)` 恢复。
- **R（结果）：** 历史 E2E 记录中，350 元工单完成 `SUSPENDED → APPROVED → COMPLETED`；128 元低风险工单直接完成自动退赔。流程同时保留 OCR、风险和节点轨迹，主管审批时有依据可看。
- **可追问：** 为什么不在 API 中直接恢复图？回答：让 Worker 成为唯一图执行者，避免 API 多实例并发执行同一状态机，也保持请求路径足够短。

### 案例二：修复并发审批导致的重复处理风险

- **S：** 并发审批联调发现，同一挂起工单在锁释放和状态检查之间存在时间窗口，可能有多个审批请求成功。
- **T：** 保证同一工单只能有一名主管成功取得审批权，并且旧锁持有者不能误删新持有者的锁。
- **A：** 锁值使用随机 token；释放锁时使用 Lua 先比较 token 再删除，避免无条件 `DEL`；更关键的是在数据库执行 `UPDATE ... WHERE status='SUSPENDED'`，以受影响行数作为最终是否抢占成功的判断。
- **R：** 历史 6 线程测试记录为 1 个 `200`、5 个 `409`。这说明仅依赖分布式锁不够，关键状态迁移还需要数据库原子条件更新。
- **可追问：** 为什么 Redis 锁后还要数据库条件更新？回答：Redis 锁是并发削峰手段，数据库条件更新才是对业务状态唯一性的最终约束。

### 案例三：处理 Checkpointer 的真实环境兼容问题

- **S：** 初始方案使用 Redis Checkpointer，但普通 Redis 7 不含 RedisJSON，E2E 运行时出现 `JSON.SET` 失败；同时 Redis Stack 镜像在环境中不可稳定获取。
- **T：** 不放弃原生挂起/恢复语义，同时让 Docker Compose 环境可运行。
- **A：** 将 Checkpointer 抽象为工厂；默认切换到 PostgreSQL Checkpointer，保留 Redis 模式作为需要 RedisJSON 的可选配置；同时对 SQLAlchemy 风格连接串进行转换，使其符合 `PostgresSaver` 的原生连接串要求。
- **R：** 历史记录表明容器内完成了挂起、审批和恢复。该经历可体现：遇到基础设施约束时，先保留核心语义，再替换依赖实现，而不是用手工序列化绕过框架能力。
- **可追问：** 为什么不直接把图状态序列化到 Redis？回答：手工序列化容易遗漏版本、恢复点和并发语义，框架 Checkpointer 对图执行状态更可靠。

### 案例四：从低吞吐定位并优化短 API 性能

- **S：** 历史首轮 Locust 压测中，短 API 吞吐约为 24 QPS，未满足目标。
- **T：** 在不改变异步决策架构的前提下，提高登录、建单、列表和健康检查等短请求的吞吐。
- **A：** 增加 Uvicorn worker 数；调整数据库连接池与 PostgreSQL 最大连接数；在演示环境降低 bcrypt cost；将工单列表限制为最近 100 条，避免全表扫描。
- **R：** 历史报告记录约 190～215 QPS、P95 小于 300 ms、错误率 0%。
- **边界：** 这组数据只覆盖短 API，不代表 OCR 或外部 LLM 的端到端时延；生产压测还应使用独立压测机并区分不同接口的 SLA。

### 案例五：稳定本地 OCR，避免核心能力依赖远程服务

- **S：** OCR 是退款凭证理解的基础，但 PaddleOCR 3.x 在 Windows 环境出现 oneDNN/PIR 执行器问题。
- **T：** 在不调用远程 OCR 服务的条件下，保证中文凭证能够稳定识别。
- **A：** 回退并固定 PaddleOCR 2.9.1 与 PaddlePaddle 2.6.2 组合；将 OCR 重型依赖与核心后端依赖拆分；在流程中将无图、识别失败和低置信度统一引流至人工审批。
- **R：** 历史报告记录识别到「退款申请单 / 订单号 20260817」，平均置信度为 0.9982。
- **可追问：** 为什么不是置信度低就直接拒绝？回答：OCR 低置信度只能说明证据不可靠，不能证明用户恶意，因此应转人工审核而不是自动拒绝。

## 6. 关键技术取舍：面试时应主动说明

### 6.1 为什么是「宁挂勿错退」

自动退款是资金相关操作。系统将金额超过 300 元、OCR 置信度低于 0.6、欺诈分不低于 50、舆情不是 `LOW` 的情况统一导向人工审批。模型调用异常也按高风险处理。该策略牺牲一部分自动化率，换取更低的错误放款风险。

### 6.2 为什么规则层必须是纯函数

LLM 适合处理分类和信息抽取，但不应承担确定性的资金路由。`decision_rules.py` 将路由写成无 I/O 的纯函数，使阈值边界能被稳定测试、复核与修改，也便于面试时解释「模型负责给风险信号，代码负责最终业务决策」。

### 6.3 为什么 Redis 和 PostgreSQL 同时存在

Redis 适合 Streams、幂等键、短时审批锁和事件发布；PostgreSQL 保存工单、审批记录、节点轨迹及默认图 Checkpoint。两者职责不同：前者解决高并发协调和异步传递，后者保存可审计的业务事实。

### 6.4 如何诚实说明当前边界

面试中不要掩盖 MVP 边界。可以主动说：当前列表接口只返回最近 100 条，因此监控页统计并非全量报表；生产环境需要将演示账号初始化和自动建表替换为迁移与安全的账号管理；SSE 鉴权和前端原生 `EventSource` 的请求头能力也应在生产版本中进一步完善。能说明边界和后续治理方向，通常比声称「所有问题都解决了」更可信。

## 8. 高频追问速答

### Q1：多 Agent 的价值是什么，为什么不用一个大 Prompt？

多 Agent 的重点不是数量，而是职责边界。OCR、风险、舆情和确定性决策有不同输入、失败方式和验证方法。拆分后，OCR 可本地替换，风险模型可切换，决策规则可单测，人工节点可独立挂起恢复。

### Q2：消息消费失败为什么还要 `XACK`？

不能直接确认。当前设计是先把工单标记为 `COMPLETED + FAILED`，写入错误码与失败轨迹，再确认消息。这样既避免消息无限重复消费，也不会让业务状态静默丢失。

### Q3：如果 Redis 宕机，系统怎么办？

Redis 同时承担队列、锁和幂等键，因此生产要做高可用、持久化、监控和故障恢复。业务事实与 Checkpoint 保存在 PostgreSQL；恢复 Redis 后可通过消息积压处理继续消费。更高要求下还可引入事务外盒（Transactional Outbox）解决数据库提交和入队之间的一致性问题。

### Q4：如何避免 LLM 幻觉直接影响退款？

LLM 只输出欺诈分和舆情等级等风险信号，不直接执行退款。最终路由由确定性阈值规则决定；模型超时或输出非法时走高风险兜底并转人工。

### Q5：你会如何把 MVP 进一步产品化？

优先补齐数据库层的幂等唯一约束与事务外盒、生产迁移和账号管理、SSE 的鉴权方案、全量统计与分页报表、Worker 重试和死信队列、指标与链路追踪。顺序依据是先控制资金与一致性风险，再提升可用性和可观测性。
