# 客诉舆情退赔决策系统验收与优化方案

日期：2026-09-07  
验收范围：顾客商城、客服订单中心、主管控制台、Agent 评测中心及其后端支撑能力。  
验收结论：**有条件通过，不建议以当前状态直接作为生产上线基线。** 核心退赔链路和权限控制已有较完整的测试保障；但角色职责边界、评测有效性、前端一致性和首屏性能仍有上线前必须治理的缺口。

## 1. 验收方法与证据

### 已执行

- 阅读前端路由、共享壳层、顾客/客服/主管页面、评测中心、评测数据模型、评测 Runner、API 与测试。
- 执行后端测试：`python -m pytest backend/tests -q`，结果 **250 passed**。
- 执行前端生产构建：`npm --prefix frontend run build`，结果 **成功**。
- 读取前端构建产物：单一主 JS 压缩后 **796.32 KB**，超过 Vite 500 KB 提示阈值。

### 未执行且原因明确

- 未完成真实浏览器多分辨率截图、登录态交互和全链路 OCR/Worker 验收：当前环境访问 Docker Desktop npipe 被拒绝，无法启动或确认全栈运行实例。
- 未执行真实支付、外部 LLM 与生产数据库演练；也不应将 `AUTO_REFUNDED` 解释为支付网关已成功退款。

后续上线验收必须补充 375px、768px、1440px 三组截图和三角色关键路径录屏，并使用部署环境完成工单创建、OCR、人工审批恢复与失败回收的实测证据。

## 2. 总体评价

| 领域 | 结论 | 依据 |
| --- | --- | --- |
| 核心退赔安全 | 基本可用 | 决策、幂等、审批锁、RBAC、OCR/安全网关均有回归测试；250 项后端测试通过。 |
| 顾客端体验 | 可演示，待打磨 | 已具备商品浏览、购物车、模拟支付、订单和退单入口；响应式规则存在，但尚无真实浏览器验收。 |
| 客服工作台 | 角色边界不足 | 客服能查订单及处理挂起退单，但与主管同用审批接口和同一页面，权限/职责表达不清。 |
| 主管控制台 | 功能丰富，信息偏散 | 有监控、工作台、审批、流程、大屏、评测与安全中心；多个入口存在重复状态和跳转语义不一致。 |
| 评测中心 | 有基础，不足以上线决策 | 覆盖规则、安全、意图、成本和时延；线上评分主要自比同一规则，难发现“规则本身错误”。 |

## 3. 角色与功能完整性

### 顾客

当前闭环为：商城浏览 -> 规格选择 -> 购物车 -> 地址/模拟支付 -> 订单 -> 提交退单 -> 查看退单。路由和后端接口均限制为 `CUSTOMER`，角色隔离测试已覆盖。

缺口：退单列表信息过少，只有退单号、原因、状态；顾客无法直接看到处理阶段、预计时效、补件要求、驳回原因或进入关联订单/退单详情。顾客端也没有明确的“客服协助”入口和状态解释，容易在自动审核中产生重复提交或投诉。

建议：以“售后服务单”替代简略退单列表，每笔提供时间线、当前责任方、下一步、证据缩略图、补件和撤销入口；提交前显示规则性提示，提交后显示不可重复提交的幂等反馈。

### 客服

当前具备订单查询、订单/退单搜索、查看凭证路径、对挂起退单批准或驳回的能力。后端允许 `CS` 与 `SV` 访问服务订单和退单队列；客服只可审批存在退单记录的工单，具备一层限制。

缺口：客服页面的两个业务入口都落在 `ServiceRefunds`，没有队列视图、优先级、SLA、客户上下文详情、结构化审核意见和审批后任务回执。更关键的是，API 与界面都允许客服直接点击“批准退款/驳回”，而产品文案将主管定义为审批人，组织职责存在冲突。

建议：明确二选一的组织模型，不能混用。

- 推荐模型：客服负责受理、补件、初审和建议；主管负责最终批准/驳回。客服提交 `recommendation`，主管队列执行 `approve`。
- 若业务确需客服小额授权：新增金额/风险分级授权矩阵、授权额度和审计字段；后端按矩阵而非角色名放行。

### 主管

当前具备实时监控、全量工单、待审批、流程、大屏、评测、安全治理等页面，且主管 API 受 `SV` 约束。审批采用 Redis 锁与数据库条件更新，核心并发安全设计合理。

缺口：`/approvals` 复用监控页面，导航名为“待人工审批”但页面同时混入失败订单；工作台和监控中均展示工单状态，造成入口重叠。主管缺少真正的审批工作台：待办排序、批量过滤、风险解释、证据预览、相似历史单、政策依据、审批备注模板、审批决策后的队列回执。

建议：主管一级导航收敛为“待办审批、运营监控、分析评测、安全治理”。“待办审批”默认只显示可处理事项，失败单独转入异常处置；把订单/工单详情作为右侧抽屉或详情页，确保审批时可看证据、规则命中和审计记录。

## 4. 前端布局与交互验收

### 已满足

- 后台壳层、表格横向滚动、移动端单列规则、键盘焦点样式和减弱动画已有基础实现。
- 顾客端的主要购买/搜索按钮使用 40-48px 高度；产品详情主操作为 AntD `large` 按钮，适合触控。
- 评测与安全页在 768px、640px CSS 断点下切换为两列/单列，结构性响应式策略合理。

### P1 问题：交互规格不统一

前端同时存在 AntD 默认按钮、`size=small`、自定义 38px/40px/42px/44px/48px 按钮和文本链接。业务上同等级的“刷新、重试、查看详情、批准退款、驳回”缺少统一高度、危险操作确认和按压状态。客服退款列表的批准/驳回按钮在窄屏虽然会换行，但未形成固定的移动端操作区。

优化方案：建立最小交互令牌而不是逐页调 CSS：后台普通按钮 32px、表格行操作 28px、主操作 40px、触控关键操作不低于 44px；相邻触控目标间距至少 8px。将审批动作固定为“查看详情 -> 选择结果 -> 填写原因 -> 二次确认”，驳回必须填写结构化原因，批准显示金额与命中规则二次确认。

### P1 问题：导航和内容层级重复

主管侧七个菜单项中，实时监控、退款工作台、待人工审批均与工单列表相关；`/approvals` 指向监控页，用户会误以为进入了独立待办。客服只有“订单中心”一个菜单，却承担订单检索与退单审批两个任务。

优化方案：按用户任务而非数据类型组织。主管 4 项导航、客服 3 项导航（订单检索、售后受理、我的待办）、顾客 4 项导航（商城、订单、售后、账户）。每个页面只保留一个首要行动。

### P2 问题：视觉语言不完全收敛

商城已经从红色促销样式覆盖为蓝色交易主色，但样式文件仍保留较多重复规则和颜色覆盖；登录页使用大圆角/渐变/阴影，后台与商城又各自一套表面规范。部分页面混用卡片圆角 0、8、12、16、20px，和“运营型工具”应有的克制一致性不符。

优化方案：定义语义令牌（背景、表面、边框、主操作、风险、成功、文本）和 4/8px 间距节奏；运营后台统一 6-8px 圆角、弱阴影或无阴影，商城可保留品牌差异但共享字体、焦点和禁用态。清理重复 CSS，以组件类承载状态，避免末尾覆盖式主题修补。

### P2 问题：页面代码可维护性

`ServiceRefunds.tsx` 和 `Returns.tsx` 等页面存在长单行 JSX，难以审查状态、可访问性和异常分支。应拆出只读列表、退单队列行、审批操作条等内部组件，并为关键状态增加前端测试。

## 5. 评测中心：现状、可行性与缺口

当前评测覆盖七类维度：

1. 退款规则 Golden：金额、OCR 置信度、欺诈分、舆情等级的确定性边界。
2. 安全网关：提示注入样本的拦截率。
3. 意图识别：样本覆盖率、退款主意图召回率。
4. 幻觉代理：LLM 可用时由 Judge 判定；Mock 时以预测与标注不一致作为代理。
5. 成本：旧 Prompt 与当前 Prompt 的 Token 变化。
6. 时延：意图链路 TTFT 和节点耗时。
7. 韧性：Fallback 原因、重试退避、DLQ 与审计状态。

结论：**作为研发回归和运行观察可行，但不适合作为生产策略正确性的唯一放行依据。** 原因如下：

- 线上“正确性”和“安全性”由实际路线与 `decide_with_reasons` 同源比较；当规则阈值或政策映射写错时，两者会同时“正确”，无法发现系统性偏差。
- `explainability` 用命中原因类别数量评分，而不是人工能否理解、证据是否充分、是否可执行。
- 编排快照从样本和本地 A/B 报告读取，页面若不显示报告生成时间、样本版本、Provider、运行 ID，容易把离线资料误读为实时健康度。
- 意图集约 30 条、Golden 固定 10 条，未见按高风险、边界、长尾、对抗、分群和版本漂移的覆盖门槛。
- 定期 Runner 可由脚本启动，但未发现持续集成或生产调度执行证据；报告追加 Markdown 也不适合趋势告警或追溯。

### 目标评测体系

评测必须分层，且只有确定性规则可以决定自动退赔：

| 层级 | 目标 | 关键指标 | 放行规则 |
| --- | --- | --- | --- |
| L0 单元与契约 | 防止规则、RBAC、锁、幂等回归 | 规则边界 100%、权限越权 0、并发审批单成功 | CI 必过 |
| L1 离线业务集 | 验证政策和业务结果 | 自动退赔精确率、人工转审召回率、错误放款率、理由充分率 | 错误放款为 0；高风险转审 100% |
| L2 安全与鲁棒 | 防注入、OCR 异常、模型失败 | 拦截率、失败安全转人工率、敏感数据泄漏率 | 高危注入拦截 100%；泄漏 0 |
| L3 运行质量 | 验证效率和可观测性 | p50/p95 时延、失败率、Fallback 率、队列滞留、成本 | 阈值由 SLO 定义，超线告警 |
| L4 人工复核 | 验证客户/业务体验 | 主管改判率、申诉率、补件率、满意度 | 按渠道和商品分群跟踪 |

离线标注集应由风控、客服、法务/合规共同维护，至少包含：128 元低风险全通过、金额边界、OCR 模糊/矛盾、欺诈高分、舆情高危、重复申请、注入/越权、模型超时、审批并发、政策冲突。每条用例保存政策版本、标注人、复核人和预期“处理结论 + 理由”。

## 6. 后端优化方案

### P0：上线前完成

- 固化客服/主管审批模型。推荐主管终审；若保留客服授权，落地额度矩阵、风险条件、审批人身份、前后状态和不可抵赖审计。
- 评测结果从“同源自评”改为“独立标注集比对”。新增评测用例版本、政策版本、模型/Prompt 版本、执行时间、样本分群和失败明细；不允许仅以平均分放行。
- 将周期评测接入 CI 与受控调度，输出结构化报告；失败时阻止策略/Prompt 发布，并保留不影响线上审批的原则。
- 对审批和退款动作补充审计事件：操作者、前后状态、规则版本、理由、关联证据 hash、请求 ID、处理耗时。禁止记录原始敏感材料到遥测。
- 恢复可用的 Docker/部署环境后，执行真实 E2E：128 元低风险自动决策、高风险人工转审、并发审批、OCR/LLM/Redis 故障、Worker 回收；归档日志作为上线证据。

### P1：两周内完成

- 服务订单与退单接口增加分页、状态/日期/责任人过滤、稳定排序和最小字段投影，避免随着订单量增长全量载入。
- 用 `asyncio.gather(..., return_exceptions=True)` 统一并行外部调用的失败归集；每个失败路径保留可解释原因、重试次数和最终安全状态。
- 新建正式迁移并维护兼容策略，禁止依赖 `create_all` 修改已有生产库；评测表、授权审计表、队列 SLA 字段均通过迁移交付。
- 对评测持久化增加监控：写入失败虽不得阻塞审批，但需单独告警，并显示“数据不完整”而不是展示误导性的平均数。

### P2：持续优化

- 将报告文件型指标迁至可查询的指标存储，按模型、Prompt、规则、渠道、商品和风险等级看趋势。
- 定义 SLO：审批队列等待、Worker 成功率、P95 时延、OCR 低置信率、Fallback 率、人工改判率；按阈值告警和复盘。

## 7. 前端改造路线

### 第一阶段：信息架构与关键动作（P0/P1）

1. 客服、主管审批能力按选定授权模型重做路由与 API 展示，避免页面许可与组织职责冲突。
2. 新建主管审批工作台，支持优先级、筛选、证据预览、规则解释、政策依据、审批意见、二次确认和完成回执。
3. 顾客售后改为服务单详情和时间线，展示当前状态、下一步和可补件操作。
4. 统一按钮、标签、危险确认、加载/禁用、空态和错误态组件；关键触控目标不低于 44px。

### 第二阶段：评测和监控可读性（P1）

1. 评测首页拆分为“发布门禁、离线质量、线上运行、成本效率、失败明细”，每项标注数据源、窗口、样本数、版本、最后运行时间。
2. 所有图表在空数据时不渲染零值图；显示“无最新运行记录”，避免把 0 当作真实指标。
3. 主管监控区分“需审批、运行异常、系统健康”，不再把所有状态塞入一个页面。

### 第三阶段：性能和质量（P2）

1. 对 ECharts 大屏、评测、安全页使用路由级动态导入，目标初始 JS gzip 小于 500 KB。
2. 为顾客、客服、主管各补一组关键路径前端测试和 Playwright 视觉回归：375/768/1440px。
3. 将长单行页面拆分为职责明确的组件，并覆盖审批禁用、网络失败、空队列、键盘操作和移动端操作区。

## 8. 上线门禁与验收清单

- 所有后端、前端构建、Golden、安全注入、沙箱拒绝和真实 E2E 均通过，并保存日志。
- 128 元订单只有金额、OCR、欺诈、舆情四项全低风险时自动决策；任一不满足必须转人工，并在界面显示原因。
- 客服和主管授权模型已书面确认，接口、路由、文案和审计记录一致。
- 三角色在 375px、768px、1440px 下无横向溢出；关键按钮尺寸和危险动作确认符合统一规范。
- 评测页展示每个指标的数据源、时间窗口、样本量、版本和失效状态；不以同源规则自比作为唯一正确性证明。
- 首包指标达到目标，评测/大屏页面按需加载；可访问性含键盘焦点、文本对比、图表替代说明、错误反馈均验收通过。

## 9. 建议的立项顺序

第一优先级是“审批权责与审计闭环”，第二优先级是“独立业务评测与发布门禁”，第三优先级是“主管审批台和顾客售后详情”，第四优先级是“设计系统收敛、前端拆包和视觉回归”。这四项完成后，系统才能从可演示的 MVP 提升为可被上市公司运营、内控和审计体系接受的业务工具。
