# Python 后端岗 STAR 项目讲解方案

> 项目：客诉舆情退赔决策系统（MVP）  
> 目标岗位：Python 后端工程师  
> 推荐时长：2 分钟

## 1. 讲解目标

在 2 分钟内让面试官建立四个明确认知：

1. 候选人理解异步任务系统，能够将 API 请求与耗时推理解耦。
2. 候选人能将多智能体拆分为职责单一、状态可审计的工作流节点，而非让模型直接控制业务流程。
3. 候选人能够处理长流程中的人工审批断点和状态恢复。
4. 候选人具备资金类业务的防御性设计意识，能处理重复请求与并发审批。

## 2. STAR 讲稿

> 我做过一个客诉舆情退赔决策系统，目标是把原来只按金额和发货状态判断的退款流程，升级为能够结合凭证识别、风控和舆情结果进行辅助决策的后端系统。
>
> **S，情境：** 原来的退款系统依赖 if-else 规则，客服需要人工查看破损照片、快递单和聊天截图；面对恶意退款或高风险投诉时，既有效率问题，也有错误自动退款造成资损的风险。
>
> **T，任务：** 我负责后端 MVP 的核心链路，要求实现低风险小额单自动退赔，高风险或不确定订单挂起交给主管审批，并且在审批后能够从原来的节点继续执行。核心原则是宁可转人工，也不能错误自动退款。
>
> **A，行动：** 我把同步接口和 AI 长任务拆开：FastAPI 接收建单请求后，先把工单事实写入 PostgreSQL，再通过 Redis Streams 投递任务，由独立 Worker 异步消费。
>
> 在智能体设计上，我没有做一个让大模型自由规划的通用 Agent，而是用 LangGraph 将业务拆成有固定边界的六个节点：Intake 初始化工单状态；OCR Agent 只做本地凭证识别；Fraud 与 Sentiment Agent 分别输出欺诈分和舆情等级；Decision 节点使用确定性规则汇总结果；HumanReview 节点只负责人工断点。这种设计让模型只处理它擅长的非结构化判断，金额放行、状态流转和权限控制仍由代码控制。
>
> 节点之间通过统一的 GraphState 传递金额、OCR 文本与置信度、欺诈分、舆情等级、决策和审批动作。多图 OCR 采用最小置信度作为整体可信度，避免一张低质量凭证被平均值掩盖；LLM 输出被限制为结构化字段，调用失败或格式非法时返回高风险保守值，最终由确定性决策规则强制进入人工审核。
>
> 对需要人工处理的订单，我没有自己序列化流程上下文，而是使用 LangGraph 原生 `interrupt()` 暂停图执行，并通过 Checkpointer 持久化断点。主管审批时，后端用 `Command(resume=...)` 恢复原图执行，因此可以保证审批前后的状态链路可追踪。
>
> 在安全性上，我把 OCR 低置信度、LLM 超时和结构化结果解析失败都统一降级为人工审核；同时用 `X-Idempotency-Key` 防止重复建单，用带随机 Token 的 Redis 分布式锁与 Lua 比较删除防止锁误删，并配合数据库条件更新，避免多个主管并发审批造成重复退款。
>
> **R，结果：** 最终验证了两条关键链路：350 元订单会在人工节点安全挂起，审批后恢复为已批准；128 元低风险订单能够自动退赔。关键的决策边界、接口幂等、锁竞态和图恢复路径均有自动化测试覆盖。

## 4. 高频追问与回答要点

### 4.1 为什么使用 Redis Streams，而不是在 FastAPI 中同步执行？

OCR 与 LLM 调用是耗时且不稳定的外部处理。同步执行会占用 API 请求连接，增加超时与扩容压力。Redis Streams 将建单和推理解耦，API 可以快速返回工单状态，Worker 可独立扩容和重试。

### 4.2 这个项目的多智能体是如何分工的？

它不是多个大模型互相对话的自由协作，而是由 LangGraph 编排的受控工作流。Intake 初始化状态，OCR 节点提取本地凭证文本和置信度，Fraud 与 Sentiment 节点分别完成风控打分、舆情分类，Decision 节点用确定性规则决定自动退款或人工审核，HumanReview 节点通过 `interrupt()` 等待主管输入。每个节点只读写统一状态中的必要字段，职责明确，便于单测、观测和替换。

### 4.3 为什么不让 LLM 直接决定是否退款？

退款属于资金风险场景，LLM 输出存在超时、格式错误和不确定性。项目将 LLM 限定为风险评分和舆情分类等非结构化判断，最终退款决策由 `amount`、OCR 置信度、欺诈分和舆情等级组成的确定性规则完成。任何模型失败都映射为高风险结果并进入人工审核，避免模型异常直接放大为资损。

### 4.4 如何保证智能体节点之间的状态不乱？

我将多智能体系统实现为受控状态机，而不是让多个 Agent 自由共享自然语言上下文，具体有五层保障：

1. **显式状态契约**：所有节点只通过统一的 `GraphState` 交接数据，字段包括金额、图片路径、OCR 文本与置信度、欺诈分、舆情等级、决策和审批动作。状态字段预先定义，避免依赖隐式全局变量或非结构化聊天上下文。
2. **单向图编排与职责隔离**：流程固定为 `Intake → OCR → Fraud → Sentiment → Decision → HumanReview`。OCR 节点只写识别结果，风控节点只写欺诈分，舆情节点只写等级，决策节点汇总上游字段；后续节点必须等前置节点完成才会执行，避免节点竞争写同一状态字段。
3. **决策收口**：智能体只产出 OCR、风险分和舆情等中间事实。是否自动退款只由无 I/O 的纯函数 `decide(amount, ocr_confidence, fraud_score, sentiment)` 判断，是最终路由的唯一来源，避免多个节点各自修改工单最终状态。
4. **按线程恢复与快照校验**：每张工单生成独立 `thread_id`，它同时关联业务工单和 LangGraph checkpoint。人工审批恢复时，Worker 用该 `thread_id` 读取图快照，再通过 `Command(resume=...)` 从 `interrupt()` 断点继续；若快照不存在或为空，则将工单标记为 `CHECKPOINT_NOT_FOUND`，不使用不完整状态继续执行。
5. **业务状态原子推进与审计**：Checkpointer 保存流程执行状态，PostgreSQL `tickets` 保存业务事实，`agent_traces` 记录节点轨迹。并发审批时，Redis 锁降低冲突窗口，数据库仅允许 `SUSPENDED → RUNNING` 的条件更新成功一次；未抢到状态的请求返回 409，不会重复投递恢复消息。

严格说，当前 `TypedDict` 主要提供静态字段约定，运行时仍需依靠节点边界与测试保证没有错误字段写入。若后续节点数量增加，我会进一步把节点输入/输出拆成更小的 Pydantic 模型，并在图边界做运行时校验。

### 4.5 为什么人工审批要用 LangGraph 的 interrupt/resume？

审批发生时，决策图已经执行到中间节点。使用原生 `interrupt()` 与 Checkpointer 保存状态后，可用同一 `thread_id` 的 `Command(resume=...)` 从断点继续，避免手工保存和恢复复杂状态导致的遗漏或版本不一致。

### 4.6 如何避免同一笔订单被多次审批？

审批接口先获取 Redis 排他锁，锁值使用随机 Token；释放时通过 Lua 脚本仅删除值匹配的锁，避免旧请求误删新锁。数据库更新同时附加状态条件，作为最终兜底，未命中时返回冲突而不是重复执行退款。

### 4.7 LLM 不可靠时为什么不多次重试后继续自动退款？

退赔业务错误放行的成本高于人工审核成本。LLM 超时、服务端错误或输出格式不合法时，仅做有限重试；失败后输出保守风险结果，强制进入人工审批，保证模型异常不会扩大为资损。

### 4.8 OCR 置信度为什么参与路由？

OCR 是后续风控和决策的输入。如果凭证文字提取不可靠，后续风险结论不应被视为可信。因此低于设定阈值时直接转人工，避免在错误输入上做自动退款。

## 5. 讲解边界

- 不宣称未验证的性能数据；当前讲解只使用已验证的核心业务场景和测试覆盖。
- 不将 LLM 作为最终退款决策者；最终自动退赔条件由确定性规则控制。
- 不展开前端展示细节；若被问及，只说明前端通过 SSE 接收状态变化并在断线时轮询降级。
