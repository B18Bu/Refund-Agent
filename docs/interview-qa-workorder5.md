# 面试 QA 库（工单 5：评测、成本优化与本地沙箱安全协作）

> 沉淀 3 个与本项目紧密相关的核心面试题与标准解答。

## Q1：如何保证 LLM 调用/观测不拖垮主业务链路？

**考察点**：异步与故障隔离。

**标准解答**：
1. 业务与模型调用解耦：FastAPI 只负责鉴权、落库、入队 Redis Streams，
   长耗时的 LLM/OCR 由后台 Worker 消费。
2. 工具调用并行化：欺诈与舆情分析用 `asyncio.gather(..., return_exceptions=True)`
   并发执行，单项异常用保守值兜底（fraud=100 / sentiment=HIGH）转人工，不取消另一项。
3. 可观测性不阻塞：Telemetry 用有界队列 + 后台发送线程，`put_nowait` 满则丢观测；
   上报失败只记日志，绝不影响审批结果；上报内容经白名单脱敏。

## Q2：Langfuse 上报失败会影响业务吗？为什么 trace_id 要贯穿整条链路？

**考察点**：可观测性设计、端到端关联。

**标准解答**：
1. 不会。上报在独立线程/队列中执行，异常被捕获仅告警；设计上“观测是副本，
   不是事实来源”，决策仍由确定性规则控制。
2. trace_id 在 Worker 处理 START 消息时生成，进入 LangGraph 状态、持久化到
   `tickets.trace_id`，RESUME 从 checkpoint 复用同一 id。这样一次申请从
   OCR、风险、决策到人工审批的所有 span 可在一个 Langfuse trace 里串联，
   支撑“单笔工单成本/耗时/路由原因”的端到端分析。
3. 接入时注意：SDK 的传递依赖（opentelemetry/protobuf）可能与本地 PaddleOCR
   冲突，可用 Langfuse 公共 REST API + 自有队列替代，避免版本冲突。

## Q3：LLM-as-a-judge 与确定性规则的关系是什么？如何避免模型破坏安全底线？

**考察点**：模型能力边界、安全治理。

**标准解答**：
1. 规则 5：模型只用于判断类任务。退赔路由、重试、数值转换等确定性逻辑
   一律由 `decision_rules.decide` 代码实现；judge 只对既有结果打分并输出
   理由，不参与路由。
2. judge 打分项为正确性/安全性/解释完整性（各 0-2），安全项为 0 或总分
   低于 5/6 时门禁失败；即使模型不可用（mock），评测仍以确定性规则闭环，
   judge 状态明确标记 SKIPPED，不允许静默跳过。
3. Golden Dataset（10 条）作为回归基线：任何 Prompt 或代码改动后，必须
   保证自动放行样例不越界、强制人工样例不漏放。
