## Q1. 系统整体架构如何设计？为什么选择多 Agent + 消息队列？

**考察侧重点**：架构分层、组件职责、解耦思路、异步化取舍。

**参考答案**：

系统是"**生产者-队列-消费者**"的异步架构，将重计算与 API 请求彻底解耦：

```text
React 前端（工作台/大屏）
   │ HTTP: JWT / X-Idempotency-Key / SSE
   ▼
FastAPI API（鉴权 RBAC / 工单 / 幂等 / 审批锁 / SSE）
   │ ① 写 PostgreSQL（工单事实）
   │ ② XADD 到 Redis Streams
   ▼
Worker（LangGraph 决策图，可横向扩容）
   Intake → OCR → 欺诈风控 → 舆情 → 金额决策
   │ 本地 PaddleOCR 推理 │ DeepSeek/Mock LLM 适配器
```

**各组件职责**：

| 组件 | 职责 | 关键点 |
| --- | --- | --- |
| FastAPI API | 鉴权、建单、幂等去重、审批（加锁）、SSE | 只做轻量 I/O，秒级响应 |
| Redis Streams | 异步任务队列 | 支持消费组、确认、断电续读 |
| Worker | 消费消息、跑 LangGraph 决策图 | OCR/LLM 是慢任务，异步化避免阻塞 API |
| PostgreSQL | 业务事实（工单/轨迹/审批） | 决策结果落库，可审计 |
| Redis | 幂等键 / 审批锁 / Checkpointer | 高并发原子操作 |

**为什么多 Agent**：把原来"if-else 硬编码规则引擎"重构为**可观测、可中断、可单独测试**的决策图。每个 Agent（节点）职责单一（OCR 只识别、风控只打分、决策只路由），失败可精确定位到节点，替换单点不影响整体。

**为什么消息队列**：OCR/LLM 推理耗时数秒，若在 API 请求内同步执行会严重拖慢响应。通过 Streams 异步化，API 只负责入队、Worker 负责消化，且 Worker 支持横向扩容扛住高峰。这是本系统 QPS 能到 380+ 的结构性前提。

## Q2. 决策流如何实现挂起与从断点恢复？为何用 interrupt() 而非手工序列化？

**考察侧重点**：LangGraph 深入理解、Human-in-the-loop、状态持久化与恢复语义。

**参考答案**：

**挂起**：决策节点判定为 `HUMAN_REVIEW`（金额超限 / OCR 低置信度 / 高欺诈 / 舆情非 LOW，任一命中即"宁挂勿错退"）时，调用 LangGraph 原生 `interrupt()` 暂停图执行，工单状态置 `SUSPENDED`。

**持久化**：图执行上下文由 **Postgres Checkpointer**（`langgraph-checkpoint-postgres`）按 `thread_id` 保存。挂起时中间结果（OCR 文本/置信度、风控分、舆情）随 `snapshot.values` 一并写入工单，主管审批前可查看完整证据。

**恢复**：主管审批 → API 仅入队一条 `RESUME` 消息（含 `resume_action`），Worker 读取 checkpoint，用 `Command(resume=...)` 注入审批结果，图从断点继续执行到终态。

**为什么不用手工 pickle 序列化**：
1. 图上下文可能含不可序列化对象，手工 pickle 语义脆弱；
2. `interrupt()` 保留的是**图执行栈的语义**（已执行节点、中间变量、等待点），恢复时能精确从暂停点继续，而 pickle 只是"把对象存起来再读出来"，没有恢复"下一步该执行什么"的能力；
3. `interrupt()` 天然支持 HITL 的等待-唤醒模型，无需自己实现消息往返。

**如何避免恢复重复执行**：已执行节点的结果都固化在 checkpoint 中，恢复时不会重跑已完成的节点；配合审批分布式锁 + 幂等键，杜绝重复审批与重复提交。

## Q3. 多主管并发审批同一工单，如何保证恰好一个成功？

**考察侧重点**：分布式锁正确性、竞态条件、双防线设计。

**参考答案**：

系统用**两道独立防线**解决"锁释放空窗期"竞态：

**第一道：Redis 分布式锁（token + Lua）**
- 加锁：`SET key token NX PX 10000`，token 为 `secrets.token_urlsafe(32)` 随机值；
- 释放：Lua 脚本**比较当前值 == 传入 token 才删除**，否则返回 0。禁止无条件 `DEL`——锁可能已过期，无条件删会误删他人重新持有的新锁。

**第二道：DB 条件更新兜底（最终防线）**
审批时执行原子条件更新：
```sql
UPDATE tickets SET status='RUNNING' WHERE id=? AND status='SUSPENDED'
```
0 行影响 → 抛 409「工单不在挂起状态」。这一步把状态原子地从 SUSPENDED 推进为 RUNNING（占位），即便锁已释放、第二个请求挤进来，它的条件更新也必然失败。

**为什么需要第二道**：Redis 锁只覆盖"加锁窗口"，但审批是"先释放锁再入队 RESUME"，释放与入队之间存在空窗期——第二个请求在锁释放后通过 `status==SUSPENDED` 检查，会造成双审批。DB 条件更新把"谁能审批"交给数据库原子判断，与锁解耦，双保险。

**实测**：6 线程并发审批同一挂起工单 → `{200:1, 409:5}`，恰好 1 个成功，5 个 409 冲突。

## Q4. 前端重复提交如何避免重复工单？

**考察侧重点**：幂等设计、Redis 原子操作、双层兜底。

**参考答案**：

**机制**：前端每次提交携带 `X-Idempotency-Key`（UUID），后端用 Redis `SET NX` 做幂等去重：

```text
key   = idem:{user_id}:{X-Idempotency-Key}
value = ticket_no（工单号）
SET key value NX EX 86400   # 24h 有效期
```

- **首次提交**：`SET NX` 成功 → 正常创建工单；
- **重复提交**：`SET NX` 失败 → 返回 Redis 中存的 `ticket_no`，查库返回**首次创建的同一工单**，不再新建。

**为什么 Redis 是唯一事实来源**：`SET NX` 是原子的，天然支持并发去重——多个请求同时带同一 key，只有一个能 SET 成功，其余全部命中已存值。DB 侧另设联合唯一索引做兜底（防御极端情况）。

**实测**：接口防重测试 T1——同 key 重放（改金额 999）返回同一 `ticket_id`，且原工单金额保持 128 不变；T4——5 个并发不同 key 全部成功且互不相同。

## Q5. Worker 消费失败时如何保证消息一致性？为何先落库再 XACK？

**考察侧重点**：消息队列可靠性、at-least-once、失败语义可审计。

**参考答案**：

Redis Streams 采用 **at-least-once** 语义：消息入队 `XADD`，Worker 用 `XREADGROUP` 消费，处理成功后 `XACK` 确认。

关键在**失败路径的落库顺序**：

```text
Worker 处理不可恢复异常
   ↓
① 先落库：ticket → COMPLETED + FAILED + error_code + error_message（mark_failed）
   ↓
② 再 XACK：确认消息已消费
```

**为什么必须先落库再 XACK**：如果先 XACK 再写库，两步之间进程崩溃，消息已确认丢弃、工单却永远停在 RUNNING——**丢单且不可审计**。先落库保证"失败结果一定被持久化"，XACK 只代表"这条消息处理完毕"，即使崩溃，工单也已经是可追踪的 FAILED 终态。

**其它可靠路径**：
- 挂起（`interrupt()`）中断 → 消息**正常 XACK**（决策流已在人工节点等待恢复，上下文在 checkpoint 中，不丢）；
- checkpoint 缺失 → 落 `FAILED + CHECKPOINT_NOT_FOUND`，可定位"恢复失败"而非静默卡死。

**设计哲学**：宁可工单 FAILED 可审计，绝不静默丢失——失败语义是业务一致性的底线。

## Q6. 压测从 QPS 24 优化到 380+，做了什么？最近连接池问题如何定位？

**考察侧重点**：性能调优方法论、瓶颈识别、真实故障排查。

**参考答案**：

**性能演进（两阶段）**：

| 阶段 | 问题 | 措施 | 结果 |
| --- | --- | --- | --- |
| 初测 | QPS 24 | — | 不达标 |
| 调优 | 单 worker / 池不足 / bcrypt cost 12 / 全表扫描 | `--workers 4`；`pool_size` 5→20；`BCRYPT_ROUNDS` 12→8；`list` 加 `LIMIT 100` | QPS 190~215 |
| 再验证 | 连接池吃满 PG 上限 | `pool_size` 收紧 10+overflow5；PG `max_connections` 100→200 | **QPS 381 / 0% 错误** |

**最近真实故障：压测全接口 500 的定位链路**（值得讲的过程）：
1. **症状**：Locust 报 86×POST /api/tickets、74×GET /api/tickets 全 500，外加断连；
2. **方向**：GET 都 500 说明不是业务逻辑，而是**数据访问层整体不可用**；
3. **证据**：PG 日志密集 `FATAL: sorry, too many clients already`；`pg_stat_activity` 显示 API 独占 **80 个连接**（4 worker × `pool_size=20`），已占 PG 默认上限 100 的 80%；
4. **根因**：SQLAlchemy 连接池是**每进程独立**的，4 个 uvicorn worker 各持有 20 连接累加 80，压测峰值再加 max_overflow 与 worker 进程连接 → 冲破 100 → PG 拒绝新连接 → 全 DB 接口 500；
5. **修复**：池收紧为 `pool_size=10 + max_overflow=5`（单进程 ≤15，4 进程 ≤60），PG 上限提到 200，留足余量；
6. **验证**：50 用户 30s 压测 11303 请求 **0 失败**，PG 日志 0 次连接拒绝。

**方法论提炼**：并发系统调优必须牢记——**连接池、worker 数、服务端上限是联动变量**，任何一项单独调大都可能让另一项成为新瓶颈。

## Q7. OCR 为何必须本地推理？LLM 为何用适配器？低置信度如何处理？

**考察侧重点**：本地推理约束、模型适配、可靠性兜底策略。

**参考答案**：

**OCR 本地推理（无远程依赖）**：MVP 硬性要求核心算法在本地容器运行，禁止远程 OCR 服务。项目集成 **PaddleOCR 2.9.1**（+ paddlepaddle 2.6.2），首次调用自动下载 PP-OCRv4 中文模型，之后完全离线推理。已验证识别「退款申请单」「订单号20260817」，平均置信度 0.998。
- **版本坑**：PaddleOCR 3.x 在 Windows 存在 onednn/PIR 执行器缺陷，最终锁定已验证的 2.x 组合。

**LLM 用 OpenAI 兼容适配器**：`LLM_PROVIDER=deepseek | mock` 一键切换。deepseek 走真实 API；mock 走本地确定性 Stub（含欺诈关键词检测、舆情分级），无密钥环境与单测可用。适配器隔离了"模型可替换性"——换模型不动业务代码。

**低置信度/异常兜底（宁挂勿错退）**：
- OCR 置信度 < 0.6 → **强制人工**（`OCR_CONFIDENCE_THRESHOLD`）；
- LLM 超时/非法输出 → 重试 1 次 → 保守兜底（Fraud=100 / Sentiment=HIGH）→ 决策层强制人工；
- 纯函数 `decide(amount, ocr_confidence, fraud_score, sentiment)` 是**决策正确性唯一来源**，任一红线命中即 HUMAN_REVIEW，绝不自动放行高风险单。

## Q8. 大屏与工作台的实时更新如何实现？Agent 流转图怎么呈现？

**考察侧重点**：前端实时通信、SSE 与降级、可视化。

**参考答案**：

**技术栈**：React 18 + TypeScript + AntD + ECharts。

**实时性三通道**：

| 通道 | 场景 | 实现 |
| --- | --- | --- |
| SSE 事件流 | 工单详情实时推送 | `EventSource /api/tickets/{id}/events`，收到 `ticket_update` 后调详情接口取全量数据 |
| 轮询降级 | SSE 断线保护 | 前端断线后切 **2s 轮询**兜底，保证状态不卡死 |
| 列表轮询 | 工作台工单列表 | 5s 轮询刷新 |

**为什么用 SSE 而非 WebSocket**：事件是**服务端单向推送**（工单状态变更 → 前端），SSE 基于 HTTP、天然支持重连与 EventSource 语义，比 WebSocket 更轻、更契合该场景。

**Agent 流转图（FlowCanvas）**：用 ECharts **有向图（graph）**渲染决策链路。后端返回 `agent_traces`（agent_name / status / sequence_no / input/output summary），前端按序绘出 Intake → OCR → 风控 → 舆情 → 决策 节点，节点状态（SUCCESS/FAILED）用颜色区分，让主管一眼看到决策流到哪一步、哪步失败。

**大屏（Screen）**：客诉舆情退赔决策实时大屏，集中展示 Agent 执行路径、OCR 识别文字与舆情风险分，供监控与演示。
