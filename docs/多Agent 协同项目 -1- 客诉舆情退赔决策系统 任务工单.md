## 2 任务描述
### 一、任务描述
#### 1 背景介绍
**旧系统现状：** 现有的电商退款模块是一个传统的"if-else"硬编码规则引擎（仅判断退款金额和是否发货）。随着多渠道客诉增加，出现大量"恶意退款/薅羊毛"事件，且用户上传的凭证（破损照片、快递单OCR、聊天截图）无法自动识别，导致人工客服审核压力极大。同时，旧的后台管理界面十分简陋，客服主管无法直观看到多Agent的决策链路和"人工审批挂起"的节点状态。

**<font style="background-color:#FCE75A;">重构需求：</font>**<font style="background-color:#FCE75A;"> 将旧系统重构为支持"</font>**<font style="background-color:#FCE75A;">多Agent协同的客诉舆情退赔决策系统</font>**<font style="background-color:#FCE75A;">"。前端需要一个现代化的工作台Dashboard，能够实时展示Agent状态流转图、客诉详情、凭证OCR识别结果、舆情风险报告，并提供</font>**<font style="background-color:#FCE75A;">一键审批/拒绝的断点干预（Human-in-the-loop）</font>**<font style="background-color:#FCE75A;">界面。</font>

#### 2 首次工单推荐实现方案（最小可上线MVP）
+ **用户模块：** 客服/主管登录、JWT鉴权、用户角色与审批权限控制；
+ **决策流模块：**基于LangGraph的多Agent协作流**（包含 OCR Agent**、**舆情风控Agent**、**金额决策Agent** )
+ **流转控制：** 决策流的三态流转（Running 运行中 → Suspended 挂起中 → Completed 已完成），在挂起状态下通过Redis序列化保存图的上下文；
+ **数据防重：** 前端提交审批防重机制（基于X-Idempotency-Key与Redis分布式锁）；
+ **大屏展示：** 直观展示Agent执行路径、OCR识别文字与舆情风险分；
+ **打包压测：** Docker Compose容器化部署、Locust压测自证。

### <font style="background-color:#FCE75A;">任务一：需求分析、前后端架构设计与任务拆解（1.5人日）</font>
#### 1.1 三方对齐机制（Human + AI-A + AI-B）
在编写任何业务代码前，必须进行三方对齐。引入两个不同类型的AI模型（如**AI-A**：逻辑分析型助手Gemini，**AI-B**：工程实现型助手Cursor/Claude Code），与**人类（学生）**共同组成评审小组，消除认知偏差与安全盲区。

#### 1.2 三方主要职责分工
**【图：三方对齐机制架构图】**

| **参与方** | **核心职责** | **关注焦点与架构设计沉淀** |
| --- | --- | --- |
| **人类 (学生/开发者)** | 1. 下达原始需求及已知限制；   2. 针对两个AI抛出的逻辑冲突、技术选型问题进行最终裁决；   3. 圈定 MVP 范围，砍掉过度设计。 | 业务合理性、开发工作量控制、系统最终交付质量。 |
| **AI-A (分析助手)   ****(例: Gemini)** | 1. **逆向转述需求并挖掘业务边界**（如 OCR 识别置信度过低、舆情风控接口超时该如何流转）；   2. 引导学生剖析异步队列与流量解耦（设计 FastAPI 接收请求后写入 Redis Streams，由后台 Worker 异步拉取执行的长周期推理模式）。 | 业务流闭环、异常场景防御、退赔安全策略、大模型调用流量解耦。 |

#### 2.1 AI协作要求：Loop Engineering（循环工程）思想

**典型案例示例：**

> **案例1：Redis状态更新并发竞态问题（Race Condition）**
>
> **潜在致命问题：** 在高并发（QPS 300+）下，若两个客服同时对同一笔订单执行"审批/拒绝"，两者同时读取到了相同的旧状态，后写入的请求会无情地覆盖先写入的请求（Lost Update丢失更新），导致状态机状态与实际退款动作不一致。
>
> **我的修改方案（自证修改）：** 我命令AI使用Redis分布式锁（setnx）或Lua脚本原子操作进行了重构。

3. **面试问题三：** 在进行压力测试（QPS 300+）时，你遇到了什么问题？是如何借助工具解决的？

## 验收标准
### 任务一：需求分析、前后端架构设计与任务拆解
1. **三方认知一致性：** 评审记录中必须体现AI提出的至少3个业务/工程架构异常点（如OCR识别超时、恶意薅羊毛判定、Redis分布式锁Key设计等），且有学生给出的明确技术裁决。
2. **规格驱动红线：** 在需求与规格文档定稿并锁死前，代码仓库中禁止出现任何业务代码提交。
3. 《核心技术架构深度剖析手册》（Markdown自述文档或脑图导出文件）必须是自己整理的，不能用AI实现。

### 任务二：基于AI编程工具的代码生成、功能实现与测试
1. AI编程工具的提示词必须体现Loop Engineering、必须要有每个阶段的LOOP验证报告；
2. **两大核心场景联调证明：** 必须自己测试、录屏提供，不能提供AI实现的证据；
3. 必须包含前后端项目源码以及单元测试脚本。

### 任务三：打包上线与压力测试
1. **一键容器化启动：** 在干净的服务器环境中执行`docker compose up -d`，全套服务（前端、后端、MySQL/PG、Redis、Worker）必须全部正常拉起，且无任何硬编码端口冲突。
2. **服务自启动与容灾：** 手动执行`docker kill`强杀后端或Worker进程，服务必须在5秒内通过健康检查策略或守护脚本自动拉起并恢复运行。
3. **性能指标达标（单机Docker环境红线）：** 在高并发压力测试下，核心接口需满足：QPS >= 200，响应时间 < 300ms，错误率 < 0.1%。
4. 压测全程系统各组件表现平稳，不得发生OOM（内存溢出）或死锁崩溃。
5. **性能优化闭环自证：** 必须提交至少一项由AI辅助分析并实施的性能优化方案（提供优化前后的数据对比图表），证明优化后系统的响应时间或吞吐量有显著改善。

### 任务四：项目总结与AI代码审查报告
1. **代码审计深度：** 审查报告中的修复用例必须真实、有效。针对AI生成代码中的各类问题，必须给出符合编程规范的修改方案并验证通过。
2. **技术面试熟练度：** 学生必须能够脱离文档，流畅、深入地回答整理出来的常问面试题。
